# 2026-11-12 Vertex AI 호출: 판정 모델과 질의 임베딩 (Rust)

## 바꾼 것
- `crates/llm/src/vertex/`(새 모듈):
  - `endpoint.rs`: 전역(`https://aiplatform.googleapis.com/v1/publishers/google/models/M:메서드`)과 지역·프로젝트 경로를 만든다. API 키는 `x-goog-api-key` 헤더로 보낸다. Debug 출력에 키가 나오지 않는다.
  - `error.rs`: `VertexError`로 응답을 분류한다.
    - 429·`RESOURCE_EXHAUSTED`·5xx·시간 초과·연결 실패는 다시 시도한다. Retry-After 헤더를 따른다.
    - 401·403은 다시 시도하지 않는다. 키나 권한 문제로 보고 오류 기록을 남긴다.
    - 그 밖의 4xx는 그 요청만 실패한다.
    - 안전 차단(`SAFETY` 등)과 출력 토큰 한도(`MAX_TOKENS`)는 각각 따로 분류한다.
  - `retry.rs`: 지수 백오프에 지터(0.5~1배)를 주고 상한을 둔다.
  - `generate.rs`: Gemini `generateContent`를 부른다. 온도 0, `responseMimeType=application/json`(JSON 모드), 생각 예산(선택)을 쓴다. 응답에서 생각 조각은 빼고 글만 모은다. 토큰 사용량을 기록한다.
  - `embed.rs`: `gemini-embedding-001` `predict`를 부른다(요청 하나에 글 하나). 작업 종류(`RETRIEVAL_QUERY`·`RETRIEVAL_DOCUMENT`)와 출력 차원을 지정하고, `autoTruncate=true`로 둔다. 받은 벡터는 L2 정규화하고 차원 수를 확인한다. 잘림 여부와 토큰 수를 돌려준다.
- `LlmClient::vertex(endpoint, model, thinking_budget)`: 판정 엔진이 같은 `complete_json`으로 Vertex를 부른다.
  - `LlmError`에 `Auth`·`Blocked`·`Truncated`를 더했다.
  - 엔진은 `Auth`를 「모델 서버 꺼짐」으로, `Blocked`·`Truncated`를 「모델 출력 해석 실패」로 처리하고, 결과를 캐시에 넣지 않는다.
- `crates/retrieval/src/embed_vertex.rs`: 서버 질의 임베딩을 Vertex로 부른다. 동시 호출 수는 기존 `EMBED_CONCURRENCY` 제한을 따르고, 3번까지 다시 시도한다.
- 서버 설정
  - 판정 모델: `LLM_PROVIDER=openai|vertex`(기본 openai). vertex이면 `LLM_MODEL`·`LLM_API_KEY`가 필요하고 `LLM_BASE_URL`은 쓰지 않는다. `LLM_THINKING_BUDGET`은 선택이다.
  - 질의 임베딩: `EMBED_PROVIDER=openai|vertex`(기본 openai). vertex이면 `EMBED_MODEL`·`EMBED_API_KEY`가 필요하다.
  - 공통: `VERTEX_PROJECT`·`VERTEX_LOCATION`·`VERTEX_HOST`(모두 선택, 비우면 전역 경로)
  - 질의 임베딩을 바꾸면 `CORPUS_EMBED_MODEL`도 DB에 등록한 새 모델 이름(예: `gemini-embedding-001@1024`)으로 바꿔야 한다. 그래야 서버가 같은 모델로 만든 벡터만 찾는다.

## 왜
- 사용자 결정(2026-11-12): GPU 비용 때문에 모델과 임베딩을 모두 Vertex AI 호출로 바꾼다.
  - 임베딩은 `gemini-embedding-001`, 1024차원이다. 지금 표 구조(halfvec(1024))를 그대로 쓰고, 기존 bge-m3 벡터는 모두 다시 만든다.
  - 모델은 사용자가 「Gemini 3.8 Flash 아르곤 카본」으로 정했다. 정확한 모델 ID는 설정으로 받는다.
- 인증은 사용자가 발급할 API 키로 한다.

## 덧붙임: 별표 벡터를 모델로 거름 (같은 날)
- 생산 쪽이 `annex_node.embed_model_id`를 더했다. 기존 bge-m3 벡터 1,367,440행에는 모델 번호 1을 채웠다(UPDATE, 35분 58초).
- 검색(`laws.rs` `vector_candidates`·`vector_ready`)은 별표 벡터도 `embedding_model.name = CORPUS_EMBED_MODEL`인 행만 본다. 그래서 다시 임베딩하는 동안 두 모델의 벡터가 섞이지 않는다.
- 실제 DB 확인: 저장된 벡터 하나로 질의했을 때 bge-m3로 거르면 40행, gemini로 거르면 0행이 나왔다(아직 Vertex 벡터 없음). retrieval 시험 35개가 통과했다.

## 덧붙임: AI Studio(Gemini API) 키와 768차원 (같은 날)
- 사용자의 키가 GCP Vertex 키가 아니라 AI Studio 키였다. Vertex 주소로 부르면 403이 난다.
  - 서버 설정 `LLM_PROVIDER=gemini`·`EMBED_PROVIDER=gemini`는 `generativelanguage.googleapis.com/v1beta/models/…`를 부른다(`VertexEndpoint::gemini`). 주소를 바꾸려면 `GEMINI_HOST`를 쓴다.
  - 설정 시험 12개가 통과했다.
- 사용자 결정으로 임베딩 차원을 768로 바꿨다.
  - 소비 쪽 `DIM`을 768로 바꿨고, 기본 등록 모델 이름은 `gemini-embedding-001@768`이다.
  - 생산 쪽은 벡터 칸을 halfvec(768)로 바꾸고 기존 벡터(bge-m3 포함)를 지운다(사용자 승인). Batch API로 다시 임베딩하며, 법령·판례 모두 최근 3년 안이 대상이다.
- 실행 스크립트(저장소 밖 `vertex_from_private.sh`)는 비공개 `.env`의 `VERTEX_API_KEY`·`VERTEX_MODEL`(지금 `gemini-3.8-flash`)을 읽어 서버·에이전트를 gemini로 띄운다.

## 덧붙임: 온프레미스와 bge-m3로 되돌림 (같은 날 16시 무렵)
- Gemini API 일괄 임베딩은 AI Studio Tier 1 할당량 때문에 느렸다.
  - Batch 대기열은 50만 토큰이라 1,200건 작업 하나에 약 6분이 걸렸다. 일반 호출은 초당 약 17~23건이었다.
  - 전체 464만 건을 끝내려면 며칠이 걸린다.
  - Tier 2 조건(지출 100달러 이상, 첫 결제 뒤 3일 이상)을 일요일까지 맞출 수 없다.
- 사용자 결정: 임베딩은 bge-m3(1024)로 되돌려 GPU Colab에서 일괄로 만들고, 모델 호출도 온프레미스(GPU 서버의 OpenAI 호환 주소)로 되돌린다.
  - DB 벡터 칸 다섯 곳을 halfvec(1024)로 되돌렸다. Gemini 768 벡터 11,573행은 지웠다.
  - 소비 쪽 `DIM`은 1024, 기본 등록 모델 이름은 `BAAI/bge-m3`다.
  - 실행 스크립트에서 Gemini로 바꾸는 줄을 뺐다.
  - Gemini·Vertex 호출 코드는 남아 있지만, 기본값이 openai라 쓰이지 않는다.
- 시험: retrieval 40개, server 26개, 시험 DB 판례 8개가 통과했다. clippy 경고는 0건이다.
