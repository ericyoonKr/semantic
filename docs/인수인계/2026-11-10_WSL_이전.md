# 2026-11-10 실행 환경을 WSL로 옮김 (DB 포함)

## 왜
- Windows에서 서버·빌드·PostgreSQL·덤프가 한 기계의 메모리(15.5GB)를 함께 쓰다가 메모리 부족으로 백그라운드 작업이 여러 번 강제로 끝났다. Windows용 PostgreSQL은 maintenance_work_mem 상한이 2GB라 벡터 색인을 크게 만들 수 없었다.
- 사용자 결정(2026-11-10): DB까지 전부 WSL로 옮기고, WSL 메모리 상한 12GB, Windows PostgreSQL은 끔.

## 지금 구성
- WSL(Ubuntu 26.04): `.wslconfig`에 memory=12GB, swap=2GB, vmIdleTimeout=-1(놀아도 끄지 않음 — 앱이 5432를 쓰므로 늘 켜져 있어야 함), networkingMode=mirrored(Windows 127.0.0.1에서 WSL 포트가 보임).
- PostgreSQL 18.6(+pgvector 0.8.1)이 WSL에서 5432로 뜨고 WSL과 함께 자동 시작. 앱 접속 주소(.env의 CORPUS_PG_URL, APP_DB_URL)는 바꾸지 않았다.
- PostgreSQL 설정(conf.d): shared_buffers 3GB, maintenance_work_mem 4GB, effective_cache_size 8GB, max_parallel_maintenance_workers 8 — 12GB 상한 기준.
- 서버 ①·창구 ⓪·에이전트 ④ 모두 WSL에서 실행. Rust는 WSL 사용자 영역 rustup(stable), 빌드 대상 폴더는 WSL 디스크(`~/semantic-target`, 동시 작업 6). z3는 공식 배포판 정적 링크, pdfium은 Windows와 같은 배포처·같은 판(7543)의 Linux 판.
- 서버 ①의 세션 데이터(RocksDB)는 WSL 디스크로 복사해서 쓴다(`/mnt/c` 위에서 RocksDB를 열지 않음).

## 옮긴 방법과 대조
- Windows PostgreSQL 17.11에서 pg_dump(디렉터리 형식, 병렬 4) → WSL PostgreSQL 18.6에 pg_restore(병렬 2) → ANALYZE.
- 대조(모두 같음): 법령 DB 표 20개와 앱 DB 표 11개의 행 수, 벡터 칸 NOT NULL 수(조문 747,960, 별표 표 마디 1,367,440), 색인 46개, 뷰 1개, 읽기 역할 권한 21개, 조문 본문 글자 수 합. 제약 수는 PostgreSQL 18이 NOT NULL을 제약으로 따로 세어 다르게 보이며, 그것을 빼면 종류별로 같다.
- 확장 판: vector 0.8.0→0.8.1, btree_gist 1.7→1.8, 나머지 같음.
- 정렬 규칙: Windows `Korean_Korea.utf8` → Linux `ko_KR.UTF-8`. 한글 정렬 결과가 같은지는 아직 재지 않았다.
- 벡터 색인(HNSW, 코사인)을 WSL에서 만들었다: 조문 벡터 1.9GB, 별표 표 마디 벡터 3.4GB(5분 47초), 둘 다 유효.

## 되돌리는 길
- Windows PostgreSQL 서비스는 멈추고 시작 유형을 수동으로 바꿨을 뿐, 데이터 폴더는 그대로다. 덤프는 저장소 밖 `semantic-data`에 남겼다.

## 안 잰 것·남은 것
- 벡터 검색의 지연·정확도(색인 효과) — 질의 임베딩용 GPU가 켜져야 잴 수 있다.
- 정렬 규칙 변경의 영향.
- 비공개 쪽(같은 WSL 클러스터의 다른 DB, 계정 처리)은 저장소 밖 인수인계서에 적었다.
