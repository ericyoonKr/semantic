# 2026-11-12 에이전트 채팅 모델을 Gemini API(AI Studio 키)로도 부를 수 있게 함

## 왜
- 사용자 결정(2026-11-12): GPU 비용 때문에 모델과 임베딩을 모두 구글 호출로 바꾼다. 이번에는 Python 에이전트의 채팅 모델만 다뤘다.
- 처음에는 Vertex AI 키로 알고 Vertex 익스프레스 주소(`aiplatform.googleapis.com/v1/publishers/google/models/...`)로 만들었다. 받은 키가 AI Studio(Gemini API) 키로 확인되어(이 키로 Vertex 주소를 부르면 403) Gemini API 방식으로 바꿨다.
- 모델 ID는 기본값을 두지 않고 `VERTEX_MODEL`로만 받는다. 이 키로 쓸 수 있는 3.8 Flash의 ID는 `gemini-3.8-flash`(ListModels 기준)이고, 사용자 확인 전이다.

## 바꾼 것
- `agent/src/semantic_agent/agent/model.py`: 모델 생성. `LLM_PROVIDER`가 `openai`(기본)이면 전과 같은 `ChatOpenAI`, `gemini` 또는 `vertex`이면 `GeminiChat`(`ChatGoogleGenerativeAI`를 이어받음, `vertexai=False`, 주소 `https://generativelanguage.googleapis.com/` 고정, API 판은 라이브러리 기본 `v1beta`)을 만든다.
- `agent/src/semantic_agent/agent/model_errors.py`: 오류 분류만 모은 파일. HTTP 상태를 통과·재시도·인증 실패로 나누고, Retry-After 머리글과 본문의 `google.rpc.RetryInfo.retryDelay`를 읽고, 기다릴 시간을 계산하고, 401/403 한국어 메시지를 만들고, 종료 사유와 입력 차단을 판정한다.
- `agent/src/semantic_agent/agent/model_transport.py`: 모델 요청이 지나가는 httpx 전송 계층. 연결·읽기 시간 제한, 재시도, 동시 호출 상한, 끊은 스트림 정리를 맡는다.
- `agent/src/semantic_agent/agent/finish.py`: 호출이 끝날 때 쓸 수 없는 응답이면 오류를 올리는 콜백(`FinishCheck`).
- `agent/src/semantic_agent/config.py`: `llm_provider`(`openai`·`gemini`·`vertex`), `vertex_api_key`(SecretStr), `vertex_model`, `vertex_thinking_level`, `vertex_thinking_budget`, `vertex_max_concurrency`. 설정 이름은 실행 스크립트가 넘기는 이름 그대로 두었다. Gemini API에는 프로젝트·지역이 없어 `vertex_project`·`vertex_location` 칸은 없앴다(환경변수가 남아 있어도 무시된다. 시험으로 확인).
- `LLM_PROVIDER=vertex`도 `gemini`와 같은 뜻으로 받는다. 이미 `vertex`로 넘기는 실행 스크립트가 그대로 돌게 하려는 것이다. Vertex AI 주소로 부르는 길은 이제 없다.
- `agent/pyproject.toml`: `langchain-google-genai==4.4.0`, `google-genai==2.25.0` 고정(변경 없음).
- 시험: `agent/tests/gemini_fake.py`(가짜 Gemini 응답), `agent/tests/test_gemini_model.py`, `agent/tests/test_model_errors.py`. 이전 이름 `vertex_fake.py`, `test_vertex_model.py`는 지웠다.

## ChatOpenAI와 맞춘 동작
| 항목 | ChatOpenAI | Gemini API |
|---|---|---|
| 온도 | 0 | 0(명시) |
| 최대 출력 토큰 | `llm_max_tokens` | 같은 값을 `max_output_tokens`로 |
| 연결·읽기 시간 제한 | `httpx.Timeout(240, connect=5)` | SDK가 시간 제한을 넘기지 않으므로 전송 계층이 요청마다 같은 값을 넣음 |
| 재시도 | `llm_max_retries`회 | SDK 재시도는 끄고(시도 1번) 전송 계층이 `llm_max_retries`회 |
| 사용량 | `stream_usage=True` | 라이브러리가 늘 `usage_metadata`를 채움 |
| 콜백 | `RepeatCut` | `RepeatCut` + `FinishCheck` |
| 도구 호출 | `bind_tools` | `bind_tools` |
| general-purpose 하위 에이전트 끄기 | 제공자 `openai` | 제공자 `google_genai` |
| `extra_body={"priority":0}` | 있음 | 없음(OpenAI 호환 서버 전용) |

- thinking: `VERTEX_THINKING_LEVEL`(minimal·low·medium·high), `VERTEX_THINKING_BUDGET`. 비우면 요청에 넣지 않는다(라이브러리 기본).

## 오류 처리
- 429와 5xx: 재시도. Retry-After 머리글(초 또는 날짜)이 있으면 그 시간에 0~1초를 더해 기다리고, 없으면 본문 `retryDelay`, 그것도 없으면 지수 백오프(1, 2, 4초… 최대 20초, 단계의 절반~전체 사이 무작위). 서버가 60초보다 오래 기다리라고 하면 바로 실패시킨다(질문 마감 `ask_timeout_s` 300초 안에 끝나야 함).
- 연결 실패·끊김(`ConnectError`, `ConnectTimeout`, `ReadError`, `WriteError`, `RemoteProtocolError`): 응답 머리글 전에 생긴 것만 재시도. `ReadTimeout`은 재시도하지 않는다(240초를 한 번 더 기다리면 마감을 넘음).
- 401/403: 재시도하지 않고 `ModelAuthError`. HTTP 상태, 구글 상태, 사유를 적고 확인할 것을 한국어로 알린다. 서버 메시지 속 키는 `***`로 가린다.
- 400·404 등: 라이브러리 오류로 넘긴다(400 문맥 초과는 요약 미들웨어가 씀).
- `FinishCheck`: `MAX_TOKENS` → 「출력 한도」, `SAFETY`·`RECITATION`·`BLOCKLIST`·`PROHIBITED_CONTENT`·`SPII`·`IMAGE_*` → 「출력 안전 차단」, `promptFeedback.blockReason` → 「입력 안전 차단」 `ModelOutputError`. 나머지 종료 사유는 통과.
- 기록: 재시도·포기·인증 실패·응답 판정 실패를 남긴다(`gemini retry ...` 등). `api/sse.py`는 예외 형식 이름만 남기므로 내용은 이 기록에서 본다.
- 동시 호출 상한 `VERTEX_MAX_CONCURRENCY` 기본 4: 질문 하나가 하위 에이전트를 2개(`SUB_CONCURRENCY`)까지 동시에 돌리므로 질문 두 개가 겹쳐도 기다리지 않는 수.
- 끊은 스트림: google-genai의 응답 객체와 스트림 생성기가 서로를 참조해 쓰레기 수집 전까지 닫히지 않는다(자리 1개로 끊은 뒤 0.2초가 지나도 자리가 비지 않고 `gc.collect()` 뒤에야 비었다). `GeminiChat._astream`이 끝날 때 그 작업에서 열린 응답을 전송 계층이 닫는다.

## 환경변수와 주소
- 기동 때 거절하는 환경변수(전과 같이 둠): `GOOGLE_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION`, `GOOGLE_APPLICATION_CREDENTIALS`.
- Gemini API 방식에서 다시 잰 것: 위 다섯 개는 각각 넣어도 라이브러리가 `VERTEX_API_KEY`를 쓰고 주소도 `generativelanguage.googleapis.com/v1beta/...` 그대로였다(5/5). 즉 이 방식에서 라이브러리가 `GOOGLE_API_KEY`·`GEMINI_API_KEY`를 우선하지 않는다. 그래서 다섯 개 거절은 지금 방식에서는 실제 해를 막지 않는다. 이 변수들이 있는 정상 환경을 막는 셈이다(지시대로 그대로 둠).
- 실제로 동작을 바꾸는 것으로 잰 환경변수
  - `GOOGLE_GENAI_USE_VERTEXAI`·`GOOGLE_GENAI_USE_ENTERPRISE`=true: Vertex 백엔드로 바뀐다. 생성 직후 확인(`_require_key_auth`)이 「Vertex AI 백엔드로 잡혔습니다」로 거절한다(시험 2개).
  - `LANGSMITH_GATEWAY`=true: 주소를 지정하지 않으면 요청과 키가 `gateway.smith.langchain.com`으로 간다(시험으로 확인). 주소를 `https://generativelanguage.googleapis.com/`으로 고정해 막았고, 생성 뒤에도 주소를 확인한다.
- 프록시 환경변수가 전송 계층을 건너뛰지 않게 `trust_env=False`로 만든다(환경변수 프록시는 쓰지 않음).
- 이 기계에는 `GOOGLE_APPLICATION_CREDENTIALS`가 있어 그대로 기동하면 거절된다. 실제 호출 확인 때는 그 실행에서만 이 변수를 뺐다.

## 잰 것
- 가짜 전송 시험 75개 통과(`test_gemini_model.py` 40개, `test_model_errors.py` 35개). 닿는 기존 시험(`test_model_limits`, `test_app`, `test_repeat_cut`, `test_subagents`, `test_loop`) 21개 통과.
- 기능을 하나씩 빼고 돌려 시험이 잡는지 확인: `FinishCheck` 뺌 → 5개 실패, 끊은 스트림 닫기 뺌 → 2개, 401을 재시도로 → 3개, 환경변수 거절 뺌 → 5개, Retry-After 무시 → 4개, 시간 제한 안 넣음 → 1개, 동시 상한 무시 → 2개, 주소 고정 뺌 → 1개, 생성 뒤 확인 뺌 → 2개.
- 환경변수 거절 검사: 시험 중 49번 불려 거절 5번(모두 거절하도록 넣은 표본), 통과 44번(깨끗한 환경). 위에 적은 대로 거절한 다섯 변수는 이 방식에서 해가 없다는 것도 함께 쟀다.
- 실제 호출 1번(2026-11-12, `VERTEX_MODEL=gemini-3.8-flash`, 스트리밍, 도구 하나 묶음)
  - 성공 기준: 오류 없이 끝나고, 도구 호출이 1개 이상이고, `total_tokens`가 0보다 크면 성공.
  - 결과: `POST https://generativelanguage.googleapis.com/v1beta/models/gemini-3.8-flash:streamGenerateContent?alt=sse` 200, 도구 호출 `find_law({"name": "행정절차법"})`, 사용량 입력 70·출력 82(그중 추론 62)·합계 152, 종료 사유 `STOP`.
  - 출력 토큰 82 안에 추론 62가 들어 있었다. thinking 토큰이 `max_output_tokens`(8000) 안에서 함께 세어진다는 뜻으로 읽힌다(한 번 잰 것).

## 아직 안 잰 것
- 실제 401/403·429 응답 본문 모양과 Retry-After를 실제로 주는지.
- 에이전트 전체(주 에이전트 + 하위 에이전트)를 이 모델로 돌린 질문. 온도 0에서 되풀이 출력이 늘지 않는지(Gemini 3 계열 안내에 온도를 기본값으로 두라는 권고가 있었던 것으로 기억함, 공식 문서로 다시 확인할 것).
- 추론 토큰 때문에 `MAX_TOKENS` 오류가 얼마나 자주 나는지.
- 동시 호출 상한 4와 이 키의 분당 한도가 맞는지.
- 동기 경로(`invoke`)에서 끊은 스트림 정리(에이전트는 비동기만 씀).
- `MAX_TOKENS`로 끊긴 스트리밍 답이 SSE에서 어떻게 보이는지.
