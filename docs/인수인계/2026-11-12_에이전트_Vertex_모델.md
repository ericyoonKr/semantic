# 2026-11-12 에이전트 채팅 모델을 Vertex AI(Gemini)로도 부를 수 있게 함

## 왜
- 사용자 결정(2026-11-12): GPU 비용 때문에 모델과 임베딩을 모두 Vertex AI 호출로 바꾼다. 이번에는 Python 에이전트의 채팅 모델만 준비했다. 임베딩은 손대지 않았다.
- 인증은 사용자가 발급할 API 키로 한다. 키가 아직 없어 실제 호출은 하지 않았다. 모델 ID도 아직 정해지지 않아 설정값으로만 받고 기본값을 두지 않았다.

## 바꾼 것
- `agent/src/semantic_agent/agent/model.py`(새 파일): 모델 생성을 `build.py`에서 옮겨 왔다. `LLM_PROVIDER`가 `openai`(기본)이면 전과 같은 `ChatOpenAI`, `vertex`이면 `VertexChat`(`ChatGoogleGenerativeAI`를 이어받음)을 만든다.
- `agent/src/semantic_agent/agent/model_errors.py`(새 파일): 오류 분류만 모았다. HTTP 상태를 통과·재시도·인증 실패로 나누고, Retry-After 머리글과 응답 본문의 `google.rpc.RetryInfo.retryDelay`를 읽고, 기다릴 시간을 계산하고, 401/403 한국어 메시지를 만들고, 종료 사유(`finish_reason`)와 입력 차단(`block_reason`)을 판정한다.
- `agent/src/semantic_agent/agent/model_transport.py`(새 파일): Vertex 요청이 지나가는 httpx 전송 계층. 연결·읽기 시간 제한을 요청마다 넣고, 재시도와 동시 호출 상한을 맡는다.
- `agent/src/semantic_agent/agent/finish.py`(새 파일): 모델 호출이 끝날 때 종료 사유를 보고 쓸 수 없는 응답이면 오류를 올리는 콜백(`FinishCheck`).
- `agent/src/semantic_agent/config.py`: `llm_provider`, `vertex_api_key`(SecretStr), `vertex_model`, `vertex_project`, `vertex_location`, `vertex_thinking_level`, `vertex_thinking_budget`, `vertex_max_concurrency`를 더했다. `missing()`은 제공자에 따라 `vertex_api_key`·`vertex_model` 또는 `llm_base_url`·`llm_model`을 요구한다.
- `agent/src/semantic_agent/agent/build.py`: `build_model`을 뺐다. `agent/src/semantic_agent/api/app.py`는 `model.py`에서 가져온다.
- `agent/pyproject.toml`: `langchain-google-genai==4.4.0`, `google-genai==2.25.0`을 정확히 고정했다. 두 판 모두 이미 `deepagents`를 통해 잠금 파일에 들어 있던 판이라 `uv.lock`은 루트 의존성 4줄만 바뀌었고 받은 패키지 판은 그대로다.
- 시험: `agent/tests/vertex_fake.py`(가짜 Vertex 응답), `agent/tests/test_vertex_model.py`, `agent/tests/test_model_errors.py`. `agent/tests/test_model_limits.py`는 가져오는 경로만 바꿨다.

- 가짜 전송 계층으로 잰 실제 요청 주소: `https://aiplatform.googleapis.com/v1/publishers/google/models/<모델ID>:generateContent`(스트리밍은 `:streamGenerateContent?alt=sse`), 키는 머리글에만 있고 주소에는 없다. SDK 기본 판은 `v1beta1`이라 `api_version="v1"`을 넣어 사용자가 말한 주소에 맞췄다.

## 오류 처리
- 429와 5xx: 재시도한다. Retry-After 머리글(초 또는 날짜)이 있으면 그 시간에 0~1초를 더해 기다리고, 없으면 본문의 `retryDelay`, 그것도 없으면 지수 백오프(1, 2, 4초… 최대 20초, 각 단계의 절반~전체 사이 무작위)로 기다린다. 서버가 60초보다 오래 기다리라고 하면 기다리지 않고 바로 실패시킨다. 질문 전체 마감(`ask_timeout_s` 300초) 안에서 끝나야 하기 때문이다.
- 연결 실패·연결 끊김(`ConnectError`, `ConnectTimeout`, `ReadError`, `WriteError`, `RemoteProtocolError`): 응답 머리글을 받기 전에 생긴 것만 재시도한다. 읽기 시간 초과(`ReadTimeout`)는 재시도하지 않는다. 240초를 한 번 더 기다리면 질문 마감을 넘는다.
- 401/403: 재시도하지 않고 `ModelAuthError`를 올린다. 메시지에 HTTP 상태, 구글 상태(`UNAUTHENTICATED` 등), 사유(`API_KEY_INVALID` 등), 확인할 것을 한국어로 적고, 서버 메시지에 키가 들어 있으면 `***`로 가린다.
- 400·404 등 나머지: 손대지 않고 라이브러리 오류로 넘긴다. 400의 문맥 초과는 라이브러리가 `ContextOverflowError`로 바꿔 요약 미들웨어가 쓰기 때문에 가로채지 않았다.
- 응답 판정(`FinishCheck`): `MAX_TOKENS`는 「출력 한도」, `SAFETY`·`RECITATION`·`BLOCKLIST`·`PROHIBITED_CONTENT`·`SPII`·`IMAGE_*` 차단은 「출력 안전 차단」, 입력 차단(`promptFeedback.blockReason`)은 「입력 안전 차단」 `ModelOutputError`로 올린다. `STOP`·`OTHER`·`MALFORMED_FUNCTION_CALL` 등은 통과시킨다(지시 범위 밖).
- 기록: 재시도마다 상태·구글 상태·시도 횟수·기다린 시간·서버가 준 시간을 경고로, 포기·인증 실패·응답 판정 실패를 오류로 남긴다. `api/sse.py`는 일반 예외의 형식 이름만 남기므로 내용은 이 기록에서 본다.
- 동시 호출 상한 `VERTEX_MAX_CONCURRENCY` 기본 4: 질문 하나가 하위 에이전트를 2개(`SUB_CONCURRENCY`)까지 동시에 돌리므로 질문 두 개가 겹쳐도 기다리지 않는 수. 자리는 응답 본문을 다 읽고 닫을 때 돌려준다.
- 중간에 버린 스트림: google-genai의 `HttpResponse`와 그 스트림 생성기가 서로를 참조해 쓰레기 수집 전까지 닫히지 않는 것을 확인했다(자리 1개로 스트림을 끊은 뒤 0.2초가 지나도 자리가 비지 않고, `gc.collect()` 뒤에야 비었다). 그래서 `VertexChat._astream`이 끝날 때(정상·예외·중단 모두) 그 작업에서 열린 응답을 전송 계층이 직접 닫게 했다.

## 비밀값
- `Settings`·모델 객체의 `repr`/`str`/JSON, 오류 메시지, 요청 주소에 키가 나오지 않는 것을 시험했다.
- 실행 환경 예시(저장소 밖 `agent.env.sh`)에는 변수 이름만 넣었다.

## 막아 둔 설정과 그 근거
- `VERTEX_PROJECT`·`VERTEX_LOCATION`에 값이 있으면 기동 때 `ModelConfigError`로 거절한다. langchain-google-genai 4.4.0은 키를 환경변수로만 넘기는데, google-genai는 프로젝트·지역이 명시되고 키가 환경변수에서 왔으면 키를 버리고 ADC(기본 사용자 인증)를 쓴다. 가짜 전송 계층으로 재 보니 실제로 키 머리글 없이 `projects/<p>/locations/<l>/...` 주소로 나갔고, 지역만 주었을 때는 이 기계의 gcloud ADC에서 프로젝트를 읽어 왔다. 4.4.2·4.5.0 소스도 같은 방식이다.
- 환경변수 `GOOGLE_API_KEY`·`GEMINI_API_KEY`·`GOOGLE_CLOUD_PROJECT`·`GOOGLE_CLOUD_LOCATION`이 있어도 거절한다. 앞의 둘은 라이브러리가 `VERTEX_API_KEY` 대신 그 키를 쓰고(시험으로 확인), `GOOGLE_CLOUD_PROJECT`는 키를 버리게 한다(시험으로 확인). `GOOGLE_CLOUD_LOCATION`은 위와 같은 경로라 함께 막았다.
- 거절 검사의 정확도: 두 시험 파일을 돌리는 동안 검사가 46번 불렸다. 막아야 할 표본 7개(설정 3가지, 환경변수 4가지)는 7개 모두 막았고(누락 0), 깨끗한 환경의 정상 설정 39개는 하나도 막지 않았다(오탐 0). 생성 뒤에는 실제로 키가 쓰이는지, 프로젝트·지역이 비었는지를 한 번 더 본다.
- 프록시 환경변수(`HTTPS_PROXY` 등)가 있으면 httpx가 전송 계층을 건너뛸 수 있어 `trust_env=False`로 만들었다. 그래서 환경변수 프록시는 쓰지 않는다. 프록시를 켠 상태에서도 요청이 전송 계층을 지나는 것을 시험했다.

## 잰 것
- 새 시험 67개 통과(`test_vertex_model.py` 32개, `test_model_errors.py` 35개). 실제 네트워크 없이 `httpx.MockTransport`로 Vertex 응답을 흉내 냈다.
- 바꾼 부분과 닿는 기존 시험(`test_model_limits`, `test_app`, `test_repeat_cut`, `test_subagents`, `test_loop`) 21개 통과. 합쳐 88개 통과.
- 시험이 실제로 잡는지 기능을 하나씩 빼고 돌려 봤다: `FinishCheck` 뺌 → 5개 실패, 버린 스트림 닫기 뺌 → 2개 실패(시간 초과), 401을 재시도로 → 3개 실패, 환경변수 거절 뺌 → 7개 실패, Retry-After 무시 → 4개 실패, 시간 제한 안 넣음 → 1개 실패, 동시 상한 무시 → 2개 실패.
- 처음 짠 전송 계층은 이미 다 읽힌 응답이면 자리를 돌려주지 않아 동시성 시험이 멈췄다. 닫힌 응답이면 바로 돌려주게 고쳤다.

## 아직 안 잰 것
- 실제 Vertex 호출 전부(키가 없음): 401/403·429 응답의 실제 본문 모양, Retry-After를 실제로 주는지, `v1` 주소에서 thinking 설정과 도구 호출이 받아들여지는지, 사용량 숫자.
- 동기 호출 경로(`invoke`)에서 중간에 버린 스트림: 에이전트는 비동기만 쓰므로 비동기 경로만 고쳤다. 동기 경로는 재시도·시간 제한·상한은 있으나 버린 스트림을 바로 닫지는 않는다.
- `MAX_TOKENS`로 끊긴 스트리밍 답은 오류가 나기 전에 이미 앞부분이 화면으로 나간다. SSE에서 어떻게 보이는지는 아직 안 쟀습니다.

## 키를 받으면 확인할 것
1. `LLM_PROVIDER=vertex`, `VERTEX_API_KEY`, `VERTEX_MODEL`을 넣고 기동해 `vertex model ready` 기록이 나오는지.
2. 짧은 질문 한 번: 주소가 `aiplatform.googleapis.com/v1/publishers/google/models/...`인지, 답과 `usage_metadata`가 오는지.
3. 도구를 쓰는 질문 한 번: 도구 호출이 오가고 general-purpose 하위 에이전트가 안 보이는지.
4. 일부러 틀린 키로 한 번: 401/403 한국어 메시지와 재시도 없음.
5. 모델 ID가 정확한지(「재미나이 3.8 플래시 아르곤 카본」에 해당하는 실제 ID). 틀리면 404가 라이브러리 오류로 나온다.
6. 온도 0이 이 모델에서 되풀이 출력을 늘리지 않는지(Gemini 3 계열 안내에는 온도를 기본값 1.0으로 두라는 권고가 있었던 것으로 안다. 공식 문서로 다시 확인할 것).
7. thinking 토큰이 `max_output_tokens`(8000)에 포함되는지, `MAX_TOKENS` 오류가 자주 나는지.
8. 동시 호출 상한 4와 Vertex 할당량이 맞는지(429 기록 빈도).

## 남은 것
- 프로젝트·지역을 API 키와 함께 쓰려면 라이브러리를 거치지 않고 `google.genai.Client(vertexai=True, api_key=..., project=..., location=...)`를 직접 만들어 넣어야 한다. 이 조합을 Vertex가 받아 주는지 확인되지 않아 하지 않았다.
- 임베딩의 Vertex 전환은 이번 범위 밖이다.
- 이 작업 중 확인용으로 지역만 준 모델을 한 번 만들어 가짜 응답으로 호출했을 때, 라이브러리가 이 기계의 gcloud ADC를 읽어 인증에 썼다(모델 호출은 가짜 전송 계층으로만 나갔다. 토큰을 새로 받으러 구글에 접속했는지는 확인하지 않았다).
