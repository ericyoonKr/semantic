## 1. 범위와 원칙

### 1.1 범위

행정법과 헌법을 중심으로 한 법률 질의응답 시스템이다. 사용자가 채팅에서 문서를 올리면,

- **사실**의 출처는 그 문서와, 사용자가 채팅에서 말한 진술이다 (원칙 3).
- **근거**의 출처는 새로 수집한 법령·판례 DB와, 법령 지식그래프다.

질문은 두 가지로 나뉜다.

- 일반 질문: 문서·법령·판례를 도구로 찾아 읽고 서술로 답한다.
- 요건 판단 질문(성립하나, 해당하나, 지났나): 요건 트리를 리프까지 나누고, LLM은 리프 하나씩만 판정하며,
  리프의 조합은 Z3가 판정한다.

채팅 세션은 LangGraph 체크포인트(PostgreSQL)에 저장해, 세션 안에서 답한 것과 에이전트가 읽은 것을 기억한다 (§10.1).

- **이 시스템은 챗봇이다. 생산물은 글 답변뿐이다.** 파일·문서·내려받기·서식 같은 산출물을 만들지 않는다. 소장·답변서·준비서면·계약서 등 법률 문서를 써 주지 않는다
  (요청이 오면 거절하고 글로 설명만 한다 — 가드레일, 구현지시서 「가드레일」). 세션 메모·사용자 설정은 내부 상태이고 사용자에게 내주는 산출물이 아니다.
- 언어: Rust가 기본이다. Python은 에이전트 호출에 필요한 부분(Deep Agents 조립, 도구 래퍼, 매번 붙이는 미들웨어, 채팅 창구)에만 쓴다.
  판정·검색·파싱·지식그래프·짧은 번호 변환·사용자 진술 원문 대조를 뺀 나머지 판단 로직을 Python에 두지 않는다.
- 이 저장소는 **소비 쪽만** 담는다: 에이전트, 업로드 문서 읽기, 법령·판례 검색(만들어진 DB를 읽기만 함), 지식그래프 읽기, 요건 판단 엔진.
  법령·판례 수집과 DB 구축, 지식그래프 생산(생산 계층)은 이 저장소에 두지 않는다(§2.1).
- 채팅 에이전트는 Python(Deep Agents·LangGraph)이다. 검색·판정·파싱은 하지 않고 Rust 내부 도구 API를 HTTP로 부른다.
- 검색·판정·파싱·수집과 핵심 로직은 Rust다. C++는 라이브러리(libz3, pdfium)를 링크하는 형태로만 들어간다.

### 1.2 원칙

1. **LLM은 원자 명제 판정기다.** 문서 구조·산술·논리·규칙 조합·상태 전이는 Rust 코드와 Z3가 정한다.
   LLM에게 전체 결론("이 처분은 위법한가?")을 묻지 않는다. 채팅 에이전트도 요건 판단은 judge 도구에 맡기고,
   돌려받은 판정 문장을 고치지 않는다.
2. **모든 실패는 Unknown·「판정 불가」 쪽으로만 떨어진다.** 오류가 확정 판정으로 바뀌는 경로를 코드에 두지 않는다.
   판정 도구에서 가장 나쁜 실패는 500 오류가 아니라 오류를 삼키고 "성립"이라고 말하는 것이다.
3. **사용자의 의견을 받되, 어디서 온 것인지 표시한다.** 허용한 것은 네 가지다.
   - 사용자가 채팅에서 말한 사실을 사실의 출처로 받는다. 출처는 「사용자 진술」로 표시한다.
   - 판정할 수 없으면 판정 불가로 끝내지 않고, 판정에 필요한 사실을 사용자에게 묻는다.
   - 사용자가 판정에 동의하지 않으면, 그 의견을 가정으로 받아 다시 판정한다. 결론에는 「가정」 표시가 붙는다.
   - 사용자가 원하는 답변 형식(길이·말투·형식)을 세션 메모에 적어 두고 따른다.
   - **허용하지 않은 것**: 도구로 읽지 않은 내용으로 답하는 것(출처 없는 일반 설명). 답변은 도구로 읽은 내용으로만 한다.
4. **매번 붙이는 것은 가볍게, 본문은 필요할 때 도구로 읽는다.** 모델 입력에 매번 붙이는 것은 규칙·카탈로그·목록·목차·세션 메모뿐이다.
   업로드 문서 본문, 법령·판례 본문, 지식그래프 노드는 에이전트가 도구로 필요한 만큼 읽는다.

### 2.1 공개 범위와 데이터 위치 (사용자 결정, 2026-11-07)

**학교에는 Rust 코드만 제출한다. DB와 JSON(JSONL 포함)은 어떤 경로로도 공개하지 않는다.** 원격 저장소(GitHub)는 비공개다.

| 대상 | 자리 | 제출 |
|---|---|---|
| Rust 코드 | `crates/`, `Cargo.toml`, `Cargo.lock` | 제출함 |
| Python 에이전트, `docs/`, `rules/`, `infer/` | 저장소(비공개) | 제출하지 않음 |
| 생산 계층(수집·파싱·DB 구축·지식그래프 생산)의 코드와 문서 | 저장소에 두지 않음 | 공개 안 함 |
| 법령·판례 DB (PostgreSQL 데이터) | DB 서버 | 공개 안 함 |
| 지식그래프 소비 묶음 | `$KG_DIR/consumer/` | 공개 안 함 |
| 지식그래프 적재본 | `$KG_DIR/sqlite/` | 공개 안 함 |
| 웹 프론트(React) | `web/` | 제출하지 않음 |
| RocksDB 세션 산출물 | `$DATA_DIR/rocksdb/` | 공개 안 함 |
| 체크포인트·Store | PostgreSQL | 공개 안 함 |

규칙:
- 데이터 경로는 모두 환경변수(`DATA_DIR`, `KG_DIR`)로 받고, 기본값은 저장소 **밖**(예: `C:\Users\ych97\semantic-data\`)이다. 저장소 안을 기본값으로 두지 않는다.
- `crates/` 아래에는 `.json`·`.jsonl`·`.db` 같은 데이터 파일을 두지 않는다. 시험 표본은 시험 코드 안에서 직접 만든다(가짜 노드 몇 개).
- **코드에는 주석을 남기지 않는다**(Rust·Python·SQL·셸·`Cargo.toml` 모두, 문서 주석 `///`·`//!` 포함). 무엇을 하는 코드인지는 `docs/구현지시서.md`에만 적는다.
- Rust 소스의 문자열(오류 문구·로그 포함)에 실제 데이터 내용(그래프 노드 문장, 판례 본문, 법령 원문 인용), 생산 계층의 경로·호스트 주소·DB 이름, 비밀값을 넣지 않는다.
- 다른 프로젝트의 코드와 문서는 가져오지 않는다. 저장소 문서는 외부 자료의 경로나 이름을 적지 않는다.
  설계 근거는 `docs/설계서.md §N`으로만 가리킨다(제출본에 docs가 없어도 주석이 데이터를 드러내지 않게).
- `.gitignore`에 데이터 확장자와 데이터 폴더를 넣어 실수로 커밋되는 길을 막는다.
- 제출본은 `crates/`·`Cargo.toml`·`Cargo.lock`만 따로 묶어 만든다. 묶기 전에 확장자가 `.rs`·`.toml`·`.lock`이 아닌 파일이 0개인지, 위 금지 문자열이 0건인지 센다.

### 2.2 모델 서버 (vLLM) — 서빙, 요청 대기열, 동시성

**구성**
- **Colab G4 GPU 하나**에 vLLM 프로세스 둘을 함께 올린다(사용자 결정 2026-11-07): 임베딩(BGE-M3, pooling 실행)과 생성(Gemma 4 26B A4B IT). 허용된 GPU 메모리 안에서 최대한 쓴다.
  - G4는 RTX PRO 6000 Blackwell(96GB)로 보인다 — 0단계에서 런타임의 `nvidia-smi`로 확인한다. 96GB면 Gemma bf16 가중치(약 52GB)와 BGE-M3(약 2.3GB)가 양자화 없이 들어간다.
  - 기동 순서와 몫: BGE-M3 먼저 `--gpu-memory-utilization 0.08` → Gemma `0.85`(가중치 뒤 남는 몫이 KV 캐시) → 0.07은 여유. 두 프로세스 몫의 합이 0.95를 넘지 않게 한다.
  - Gemma의 `--max-model-len`과 `--max-num-seqs`는 기동 로그의 KV 캐시 크기(최대 동시 처리 수)를 보고 정하고, 그 숫자를 여기 적는다. 둘이 GPU 메모리를 나눠 쓴다
  (몫은 아래 G4 항목).
- 생성 서버 기동 인자(값은 0단계 실측 후 확정):

| 인자 | 제안 | 이유 |
|---|---|---|
| `--max-model-len` | Gemma 4 문맥 한도 이하에서 GPU 메모리에 맞는 값 | 리프 판정은 문서 전문을 넣을 수 있어 길다(§9.1) |
| `--max-num-seqs` | 16 | 동시에 디코딩하는 요청 수. 리프 fan-out 상한(§11)과 맞춘다 |
| `--max-num-batched-tokens` | 8192 | 긴 프롬프트의 prefill이 다른 요청의 디코딩을 오래 막지 않게 chunked prefill과 함께 |
| `--enable-chunked-prefill` | 켬 | 위와 같음 |
| `--enable-prefix-caching` | 켬 | 리프마다 같은 문서가 앞에 오고(§9.1), 에이전트는 시스템 프롬프트가 매번 같다 |
| `--enable-auto-tool-choice` `--tool-call-parser gemma4`(확인 필요) | 켬 | 에이전트 도구 호출. Gemma 4는 JSON이 아니라 전용 토큰으로 도구를 부른다. 이름은 0단계에서 쓸 vLLM 판으로 확인 |
| 생각 구간 | 생각 파서를 켜거나, 안 되면 ⓪가 걸러 냄 | 일부 vLLM 판에서 생각 글이 답변에 섞여 나온다는 보고가 있다 — 프론트로 내보내지 않는다(§20) |
| `--scheduling-policy priority` | 켬 | 아래 우선순위 |
| `--api-key` | 환경변수 | 터널로 밖에 열리므로 키 필수 |
| `--served-model-name` | `gemma4`, `bge-m3` | 호출 쪽 설정이 모델 경로에 묶이지 않게 |

**요청 대기열과 우선순위**

vLLM은 받은 요청을 대기열에 넣고 연속 배치(continuous batching)로 처리한다. 대기열이 길어지면 요청을 거절하지 않고 기다리게 하므로,
호출하는 쪽이 시간 제한과 동시성 상한을 반드시 가진다.

| 우선순위 | 호출 | 보내는 곳 | 이유 |
|---|---|---|---|
| 0 (가장 높음) | 채팅 에이전트의 모델 호출(도구 선택·서술) | ④ `ChatOpenAI` | 사용자가 화면 앞에서 기다린다 |
| 1 | 쿼리 재작성, 질의 임베딩 | ③ | 검색 한 번이 이 호출을 기다린다 |
| 2 | 리프 판정 fan-out | ⑤ | judge 한 번에 수십 건. 묶음으로 기다려도 된다 |
| 3 | 대량 작업(생산 계층의 배치 호출이 같은 서버를 쓸 때) | 생산 계층 | 대화가 없을 때 돈다 |

- 요청마다 `priority` 값을 실어 보낸다(OpenAI 호환 API의 추가 인자 — 이름과 동작은 0단계에서 확인). 확인되지 않으면 아래 동시성 상한만으로 나눈다.
- 대량 임베딩(우선순위 3)은 서비스 시간과 겹치지 않게 돌리거나, 겹칠 때는 동시 요청 수를 1로 낮춘다.

**호출하는 쪽의 동시성 상한** (서버 전체 `--max-num-seqs` 안에서 나눈다)

| 호출하는 쪽 | 상한 | 장치 |
|---|---|---|
| ④ 에이전트 | 세션당 실행 하나(§11) | 세션별 `asyncio.Lock` |
| ③ 쿼리 재작성·임베딩 | 4 | `llm::limits::LlmLimiter`(semaphore) |
| ⑤ 리프 판정 | 8 (판정 하나 안에서), 서버 전체 12 | `LlmLimiter` 두 단계 |
| 생산 계층 배치(같은 서버를 쓸 때) | 생성 2, 임베딩 배치 동시 2 | 그쪽 설정 |

**과부하·장애 때의 동작**
- 시간 제한: 대기 시간까지 포함한 전체 마감을 호출 쪽이 건다(`tokio::time::timeout`, Python `httpx` timeout). 마감을 넘기면 원칙 2대로 떨어진다(§12).
- 재시도: 연결 실패·5xx·429만, 지수 backoff와 횟수 제한. 대기열이 길어서 늦는 경우(마감 초과)는 다시 보내지 않는다 — 같은 요청을 또 쌓지 않기 위해.
- 대기열 감시: vLLM `/metrics`의 대기 요청 수(`num_requests_waiting`)와 KV 캐시 사용률을 ①이 주기적으로 읽는다. 대기 요청이 기준(설정값)을 넘으면
  리프 판정의 동시 상한을 절반으로 낮추고, 다시 줄면 되돌린다. 기준값은 0단계 부하 시험에서 정한다.
- 상태 확인: 기동 때와 1분마다 `/health`·`/v1/models`. 응답이 없으면 「모델 서버 응답 없음」 상태로 두고 §12의 강등 규칙을 따른다.

**Colab과 터널**
- 로컬(①·④)에서 Colab으로는 터널로 부른다. 터널마다 응답 시간 상한이 있을 수 있다(예: 일부 터널은 100초 안팎에서 끊음) —
  0단계에서 쓸 터널의 상한을 재고, 긴 응답은 스트리밍으로 받아 연결이 쉬지 않게 한다.
- Colab 세션이 끊기면 다시 띄우는 노트(`infer/`)를 둔다. 모델 가중치는 다시 받지 않도록 Colab 쪽 영구 저장소에 캐시한다.
- 주소와 키는 환경변수(`LLM_BASE_URL`, `EMBED_BASE_URL`, `LLM_API_KEY`)로만.

**잰 것** (2026-11-07, BGE-M3, 이 PC → 임시 터널 → Colab): 같은 문장 두 번 cosine 1.000000, 한 문장 330ms(첫 호출 1,001ms), 배치 1·8·32·64에서 초당 4.3·7.2·8.2·8.5문장. 처리량이 배치를 늘려도 거의 늘지 않아 병목은 터널 쪽으로 보인다(원인은 아직 안 잼 — Colab 안에서 같은 배치를 재서 가른다).

**잴 것** (0단계): 동시 요청 1·4·8·16에서 생성 처리량(토큰/초)과 지연(첫 토큰·전체), 같은 문서를 앞에 둔 리프 판정 8건의 접두 캐시 적중 효과,
임베딩 배치 크기별 처리량, 터널 응답 시간 상한.

## 5. 채팅 에이전트

### 5.1 에이전트 루프와 종료 장치

에이전트는 「모델이 판단 → 도구를 부르면 실행 → 결과를 대화에 넣고 다시 모델 호출」을 반복하고,
모델이 도구를 부르지 않고 답을 내면 끝난다. 도구가 실패하면 예외로 루프를 깨지 않고
「검색 실패: 사유」·「판정 불가: 사유」 문자열을 결과로 돌려준다 (§12). 모델은 그 결과를 보고 다시 시도하거나 답변에 밝힌다.

종료 장치(값은 0단계에서 deepagents 0.7.19 기본값을 확인한 뒤 확정한다):

| 장치 | 제안 값 | 이유 |
|---|---|---|
| 최대 단계(LangGraph `recursion_limit`) | 60 | 문서 grep → 읽기 → 법령 검색 → 판례 검색 → judge → 서술이 한 질문에 20단계 안팎. 그 세 배 |
| 질문 하나의 전체 시간 | 300초 | judge는 리프 판정을 병렬로 돌려도 수십 초가 걸린다. Colab 지연을 더해 여유를 둔다 |
| 도구 호출 하나의 시간 | 검색 30초, judge 180초 | `config.py`의 `rust_timeout_s`. judge는 리프 판정 fan-out이라 길다 |
| 모델 입력 토큰 | 모델 문맥 한도의 85%에서 앞부분 요약(deepagents 기본) | §10.1 |

어느 장치에 걸려 끝나면, 그때까지의 진행을 「제한에 걸려 중단됨: 장치 이름」으로 답변 끝에 밝힌다.

대화 메시지로 넣지 않으므로, 대화가 길어져 앞부분이 요약되어도 사라지지 않는다.

### 5.4 메인과 하위 에이전트 (사용자 결정 2026-11-07)

deepagents의 기능(계획 도구 `write_todos`, 하위 에이전트 `task`, 파일 도구, 요약)을 쓰고, 일을 메인과 서브로 나눈다.

| 역할 | 맡는 일 | 도구 |
|---|---|---|
| **메인** | 대화, 질문 나누기와 계획, 서브에 맡기기, judge 호출, 최종 답변 작성, 세션 메모·사용자 설정 갱신 | `write_todos`, `task`, `judge`, 파일 도구(메모·설정 쓰기, 업로드 읽기) |
| **서브 1 `researcher`** — 자료 조사 | 법령·판례 검색과 읽기, 판례↔조문 인용 따라가기 | `search_laws`, `search_cases`, `read_law`, `read_case`, `case_citations` |
| **서브 2 `doc_reader`** — 문서 읽기 | 업로드 문서에서 질문에 맞는 대목 찾기 | `ls`, `grep`, `read_file`(읽기 전용 — `/uploads/**`만) |
| **서브 3 `kg_explorer`** — 지식그래프 탐색 | 개념·위임 관계를 여러 단계 따라가기 | `kg_find`, `kg_expand` |

- **judge는 메인만 부른다.** 판정 문장이 메인을 거쳐 원문 그대로 나가야 한다(원칙 1).
- **서브의 결과 형식**: 서브가 읽은 도구 결과는 세션 기억에 남지 않으므로(§10.1), 서브는 정해진 형식으로만 돌려준다 —
  `[{주장 한 줄, 출처(법령명·조문·시행일 | 법원·사건번호·선고일 | 파일·쪽 | 그래프·노드 번호), 원문 인용}]`와 「찾지 못한 것」 목록.
  메인은 이 결과만 근거로 쓰고, 출처 없는 줄은 쓰지 않는다. 형식에 맞지 않는 결과는 메인이 한 번 다시 맡기고, 그래도면 「자료 조사 실패」로 다룬다.
- **인용 검증**(구현지시서 B)은 ①이 차례마다 실제로 돌려준 출처 기록으로 하므로, 메인이 불렀든 서브가 불렀든 그대로 작동한다.
- **미들웨어를 명시적으로 넘긴다**: 선언형 하위 에이전트는 메인의 미들웨어를 물려받지 않는다. 서브마다 가드레일(도구 인자 검사, 같은 호출 되풀이 차단, 자료 감싸기)과 마감·단계 상한을 넘긴다.
- **기본 general-purpose 하위 에이전트는 끈다.** 위 셋만 둔다.
- **동시 실행**: 한 질문 안에서 서브는 동시에 2개까지(Colab G4 한 GPU에 Gemma 하나 — §2.2). 서브의 모델 호출도 질문 하나의 토큰 예산과 사용자별 몫(구현지시서 F·G)에 넣어 센다.
- **서브의 단계 상한**: 서브 하나에 최대 20단계, 120초. 넘으면 그때까지 찾은 것과 「제한에 걸림」을 돌려준다.
- **계획**: 질문이 둘 이상의 갈래(예: 업로드 문서 + 판례 + 요건 판단)를 품으면 메인이 `write_todos`로 계획을 세우고 갈래마다 서브를 맡긴다. 한 갈래면 계획 없이 바로 한다.

### 5.5 프롬프트 규칙

1. 요건 판단형 질문(성립하나, 해당하나, 지났나)은 스스로 결론을 내지 않고 judge를 부른다.
   judge가 돌려준 판정 문장(결론·판정 범위·Unknown 목록·가정 표시·사용자 진술 표시)은 고치거나 빼지 않는다. 서술은 그 뒤에 덧붙이기만 한다.
2. 일반 질문은 도구로 읽은 내용(업로드 문서, 사용자 진술, 법령·판례, 지식그래프)으로만 답하고, 문장마다 출처를 단다.
   출처 없는 일반 설명은 하지 않는다.
3. 도구가 「검색 실패」·「판정 불가」를 돌려주면 답변에 그대로 밝힌다. 추측으로 채우지 않는다.
4. 앞에서 읽은 자료를 다시 쓸 때, 메시지에 일부만 남은 큰 결과는 `read_file`로 원문을 다시 연다.
5. 업로드 문서는 매번 붙는 목차를 보고 `grep`으로 위치를 찾은 뒤 `read_file`로 그 범위만 읽는다. 통째로 읽지 않는다.
6. 자료 조사·문서 읽기·지식그래프 탐색은 §5.4의 서브(`researcher`·`doc_reader`·`kg_explorer`)에 맡기고, 서브가 돌려준 출처·인용만 근거로 쓴다. judge는 메인이 직접 부른다.
7. **사용자 진술**: 사용자가 문서에 없는 사실을 말하면, 그 말을 원문 그대로 세션 메모의 「사용자 진술」 칸에 적고,
   judge를 부를 때 `user_facts`에 원문 그대로 넘긴다. 바꿔 쓰지 않는다 (§9.1에서 원문 대조를 한다).
8. **필요한 사실 묻기**: judge 응답에 「필요한 사실」 목록이 있으면, 판정 문장 뒤에 그 질문을 사용자에게 그대로 묻는다.
   사용자가 답하면 규칙 7로 기록하고 judge를 다시 부른다.
9. **가정으로 다시 판정**: 사용자가 「그 부분은 인정된다고 보자」처럼 판정에 동의하지 않으면, 그 노드를 `assumptions`에 넣어
   judge를 다시 부르고, 세션 메모의 「가정」 칸에 적는다.
10. **답변 형식**: 사용자가 길이·말투·형식을 요구하면 `/prefs/answer_style.md`(Store, 대화를 넘어 유지)에 적고 이후 답변에서 따른다.
    사실·가정·판정은 여기에 적지 않는다(대화를 넘지 않게). 판정 문장 원문은 형식 요구와 상관없이 고치지 않는다.

### 5.6 세션 메모 (`/memory/session.md`)

에이전트가 `edit_file`로 고치는 파일이다. 칸은 고정한다.

```markdown
## 사용자 진술      (원문 그대로, 말한 차례 번호와 함께)
## 가정            (node_id = 값, 사용자가 말한 원문)
## 판정 이력        (claim_type / node_id / 결론 한 줄 / 차례 번호)
```

세션 메모는 매번 모델 입력에 붙으므로(§5.2), 대화가 요약되어도 이 세 가지는 남는다. 답변 형식은 세션 메모가 아니라 사용자 설정(§10.3)에 둔다.
세션 메모는 사실의 출처가 아니다. 사용자 진술의 출처는 그 진술이 들어 있는 사용자 메시지다 (§9.1).

## 6. 업로드와 문서 읽기

### 6.1 흐름

1. 사용자가 파일을 올리면 ④ `POST /session/{id}/upload`(multipart)로 들어온다. 같은 세션에서 답하던 질문은 취소하고
   업로드를 먼저 처리한다(문서 수정판 우선, §11). Rust 쪽에서 진행 중이던 판정은 「판정 불가: 문서 수정판 도착」으로 끝난다.
2. ④는 파일을 Rust `POST /sessions/{sid}/files`로 그대로 넘긴다.
3. Rust:
   1. 받기 검사: 파일명 정리(NFC, 180자), 매직 바이트(`%PDF-`, `PK`, `D0CF11E0`), 크기 상한 200MB·쪽 상한 500·글자 상한 500만,
      zip 폭탄 검사(항목당 64MB, 합계 96MB, 압축률 250 초과 거부). 값은 설정으로 둔다.
   2. 파싱(§6.2) → 통합 문서 모델(§6.3).
   3. 결정론 검증(§6.5).
   4. 쪽 표시가 들어간 글자(`--- p3 ---`)와 목차를 만든다. 쪽 번호만 있는 줄("-1-")은 공백으로 바꿔 글자 위치를 보존한다.
      글자 위치 → Block·Anchor 대응표도 함께 만든다 (§9.1의 인용 대조에 쓴다).
   5. RocksDB `state`에 한 번에(WriteBatch) 저장: 문서 모델, 쪽 표시 글자, 대응표, 검증 결과.
   6. 응답: `file_id`, 파일명, 형식, 쪽수, 글자 수, 목차, 쪽 표시 글자, 추출하지 못한 부분, 검증 결과 (§13.2).
4. ④는 쪽 표시 글자를 세션 파일 `/uploads/{file_id}.md`에 넣고, 목록·목차를 세션 상태 `uploads`에 더한다.
   대화에는 「[업로드] 파일명, 쪽수, 추출 불가 부분」 한 줄만 넣어 화면 기록에 남긴다. 본문은 대화 메시지에 넣지 않는다
   (deepagents는 5만 토큰을 넘는 사용자 메시지를 파일로 빼내고, 대화가 길면 요약한다 — 본문이 그 과정에서 빠지지 않게).
5. 조항 번호 부여와 청크 임베딩은 업로드 때 하지 않는다. 조·항·호 판별은 목차를 만들 때와 리프 판정의 인용을 표시할 때 쓴다.

같은 세션에 같은 파일을 다시 올리면 내용 해시로 새 `file_id`를 만든다. 결정론 검증은 전체를 다시 돌리고,
리프 판정은 cache_key가 바뀐 것만 다시 한다 (§9.7).

### 6.2 형식별 파싱

난이도: DOCX·HWPX 쉬움(표 구조가 XML에 있음) → PDF 어려움 → PDF 표가 가장 어려움.

| 형식 | 방법 | 표 |
|---|---|---|
| DOCX | zip + quick-xml로 OOXML을 직접 읽는다. 자동 번호(numbering.xml)를 복원하고, 각주를 읽는다. 쪽 경계는 `lastRenderedPageBreak`·`br type=page`·`pageBreakBefore`로만 안다 | `<w:tbl>` 구조. `gridSpan`(가로 병합)·`vMerge`(세로 병합) 처리 |
| HWPX | 같은 방식(zip+XML, KS X 6101), `Contents/section*.xml` | `<hp:tbl>` 구조, `cellSpan` |
| HWP(구형) | 받지 않는다. 「HWPX, DOCX 또는 글자가 들어 있는 PDF로 저장한 뒤 다시 올려 주세요」 안내 (결정 3 기본값) | — |
| PDF(글자 있음) | pdfium — 글자와 좌표(bbox) | 구조가 없어 기하로 다시 만든다 (§6.4) |
| PDF(스캔) | 받지 않는다. 「추출 불가·판정 불가」 안내 | — |

DOCX의 자동 번호(numbering.xml)와 각주, 표 셀 구조·병합·좌표는 이 설계대로 만든다.

파서는 판정의 입구이므로, 실제 문서 표본으로 추출 정확도(특히 표 셀 배정)를 잰 뒤 저장 경로에 붙인다.

### 6.3 통합 문서 모델

파서가 셋이어도 출력은 하나다 (`crates/docmodel`, 구현됨).

```rust
enum Block { Heading { level, text, anchor }, Para { text, anchor }, Table(Table) }
struct Table { cells: Vec<Cell>, anchor: Anchor, degraded: bool }   // Cell: row, col, rowspan, colspan, text, anchor
struct Anchor { source: FileId, page: Option<u32>, bbox: Option<Rect>, path: Option<String> }
```

- 모든 값은 Anchor를 달고 다닌다. Anchor 없는 값은 Z3·산술 검증에 들어가지 못한다.
- 표를 평문으로 뭉개지 않는다. 과징금 산정 내역, 별표 금액 합계가 「합계 = 부분합」 검증과 Z3 산술의 입력이다.
- 표를 글자로 바꾸는 일은 `Table::to_markdown` 하나만 한다(구현됨). 세션 파일의 글자와 리프 판정에 넘기는 글자가 같은 글자를 쓴다.
- **바꿀 점(4단계)**: 사용자 진술도 사실의 출처가 되므로 Anchor의 출처를 `enum FactSource { File(FileId), UserMessage { message_id } }`로
  넓히고, 쪽 표시 글자 안의 글자 위치 `(start, end)`를 더한다. `docs/구현지시서.md`의 anchor.rs 「다시」 항목.

### 6.4 PDF 표 재구성

괘선 있는 표는 pdfium에서 선분을 뽑아 수평·수직선을 격자로 맞추고 → 셀 사각형을 만들고 → 글자를 bbox 중심으로 셀에 배정한다
(Camelot lattice와 같은 알고리즘, Rust로). 배정되지 않은 글자 비율이 기준을 넘으면 실패로 보고 표를 만들지 않는다.
실패한 표는 평문으로 낮추고 `degraded = true` — 산술 검증과 Z3 입력에서 빠진다. 애매하면 실패가 맞다.

괘선 없는 표는 페이지를 이미지로 만들어 멀티모달 LLM에 JSON 추출을 맡긴다. 이렇게 뽑은 표에는 신뢰 등급을 낮췄다는 표시와
원문 페이지·좌표 인용을 반드시 붙인다. Gemma 4가 이미지 입력을 받는지는 0단계에서 확인한다(못 받으면 이 경로는 「추출 불가」).

### 6.5 결정론 검증

LLM을 쓰지 않고 코드로 검사한다 (`crates/checks`).

- 날짜 글자 해석(`dates.rs`), 법정 기간 마감일(`periods.rs`, 민법 제157·160·161조).
- 표의 합계·비율(`sums.rs`) — `degraded` 표는 검사하지 않는다.
- 조항 참조(`refs.rs`) — 「제N조」 참조 대상이 있는지, 참조 순환, 「별표N」 종점.

검사마다 맞는 표본(막지 않는지 = 오탐)과 일부러 틀린 표본(놓치지 않는지 = 누락)으로 정확도를 잰 뒤 결과를 사용자에게 보인다.

### 6.6 에이전트가 문서를 읽는 방법

- 매번 붙는 목록·목차를 보고, `grep(pattern, path="/uploads/{file_id}.md")`로 위치를 찾고, `read_file(path, offset, limit)`로 그 범위만 읽는다.
- 출처는 파일명과 쪽 번호(`--- pN ---` 표시)로 단다.
- 임베딩 검색은 처음에는 넣지 않는다. 글자 검색으로 부족하다는 것이 표본에서 확인되면 그때 붙인다(후보: §4 ⑦을 도구로 노출).
- `/uploads/**`는 `FilesystemPermission(operations=["write"], paths=["/uploads/**"], mode="deny")`로 쓰기를 막는다
  (deepagents 0.6.1 소스에서 이 형태를 확인했다. 0.7.19는 0단계에서 확인).

## 7. 법령·판례 검색

### 7.1 법령·판례 DB — 읽기만 한다

- 법령·판례 DB는 이 저장소 밖의 별도 생산 계층이 만든다. 이 저장소는 그 DB를 **읽기만** 한다(읽기 전용 계정, 접속 문자열은 환경변수 `CORPUS_PG_URL`).
- 소비 쪽이 기대하는 표와 열(읽기 계약)은 §14.1에 있다. 생산 계층이 표를 바꾸면 읽기 계약을 먼저 맞춘다.
- 기간: 최근 5년 판례와, 그 기간에 걸치는 법령 판본만 들어 있다고 가정한다(창 밖 판본을 인용한 판례는 판본 칸이 비어 있을 수 있다).

### 7.2 검색

```
질문 → 쿼리 재작성(LLM 1회 + moka 캐시) ─┬─ 글자 검색 후보 80건
                                          └─ 질의 임베딩 → 벡터 후보 80건
                         → RRF(k=60)로 합침 → 필터(분야·심급·선고일·현행) → 상위 k
```

- 쿼리 재작성: 일상어를 법률어로 바꾼다. 실패하면 원 질의로 검색한다(강등이지 중단이 아님). 검색 지연의 대부분이
  이 LLM 호출이므로 캐시를 둔다(지연은 0단계에서 잰다). 같은 키의 동시 미스는 moka `get_with`로 하나로 합친다.
- 재작성과 질의 임베딩은 `tokio::join!`으로 동시에 한다.
- 글자 검색 방식(형태소)은 0단계에서 정한다. 후보는 PostgreSQL 안의 방식만 둔다(pg_bigm, pg_trgm, 한국어 형태소 사전을 붙인 텍스트 검색 설정). 별도 검색 엔진은 두지 않는다.
  성공 기준: 행정법 질문 표본에서 기대한 조문·판례가 상위 k에 드는 비율과 지연. 형태소 없는 'simple' 설정이나
  색인을 타지 못하는 질의는 쓰지 않는다(질의마다 EXPLAIN으로 색인 사용을 확인).
- 필터는 조인으로 건다(`IN (SELECT …)`는 HNSW 색인을 쓰지 못하게 할 수 있다). 좁은 필터(예: 대법원만)는
  심급별 분할 또는 부분 HNSW로 푼다 — 0단계 표본으로 비교해 정한다.
- 판례↔조문: `case_citations` 도구가 `decision_citation`을 읽는다. 조문 쪽에서 판례를 찾을 때는 논리 키로 찾으므로,
  조문이 개정되어도 같은 조문을 인용한 판례가 나온다.
- 결과 문자열에는 항목마다 출처를 붙인다. 법령: 법령명·조문(또는 별표)·시행일·판본 일련번호. 판례: 법원·사건번호·선고일·절 역할.
- 강등 규칙(§12): 임베딩 서버가 응답하지 않으면 글자 검색만으로 → 결과 첫 줄에 「강등: 벡터 검색 꺼짐」.

## 8. 지식그래프

지식그래프는 이 저장소 밖의 생산 계층이 만들어 **소비 묶음**으로 넘긴다. 이 저장소는 그 묶음을 읽어 탐색만 한다.

### 8.1 입력 — 소비 묶음

- 묶음 하나는 폴더 하나다: 그래프마다 JSONL 파일 하나 + 목록 파일(`manifest.json`: 그래프 이름·파일·sha256·모양) + 목록 서명(`manifest.json.sig`).
- 묶음은 저장소 밖 `$KG_DIR/consumer/<묶음 이름>/`에 둔다(§2.1).
- JSONL 한 파일의 꼴:
  - 1행은 머리: 형식 이름(설정값 `KG_CONSUMER_SCHEMA`와 같아야 함), 그래프 이름, 모양, 계약(허용 노드 종류·허용 관계), 측정 상태,
    법령 판본 표, 건수(`counts`: 노드·간선·상태), 글 표(되풀이되는 인용문·사유를 한 번만 둔 목록).
  - 2행부터 한 줄에 항목 하나: 노드, 간선, 그래프 항목에 걸리지 않은 상태.
  - 항목은 글 표를 번호로 가리킨다. 읽을 때 되돌린다.
  - 노드의 「모름」·「해당 없음」·「판단 안 함」은 그 노드의 상태 칸에 붙어 온다. 소비 쪽은 이 값을 바꾸지 않고 그대로 보인다.
- 모양은 나무·흐름·항목 목록·찾아보기·연결망·시점별 가운데 하나다. 모양의 차이는 노드 종류와 계약의 허용 관계로만 나타난다.
- 판례 본문은 묶음에 없다. 판례↔조문은 법령·판례 DB의 인용 표에서 읽는다(§7).
- 형식 이름과 목록 형식 이름은 설정값(`KG_CONSUMER_SCHEMA`, `KG_MANIFEST_SCHEMA`)으로 받는다. 코드에 박지 않는다.
- 지금 받은 묶음: 헌법 개념 그래프 하나(모양 「연결망」). 이름·건수·대조 결과는 저장소 밖 기록에 있다.

### 8.2 적재 — 그래프마다 읽기 전용 SQLite (사용자 허용, 2026-11-07)

지식그래프만 예외로 SQLite를 쓴다. 나머지 저장소는 PostgreSQL과 RocksDB뿐이다(§2).
이 PC(메모리 15.5GB)에서 PostgreSQL에 쓰기 부담을 더하지 않고, 그래프 하나를 파일 하나로 바꿔 끼울 수 있어서다.

서버(①)가 기동할 때 `$KG_DIR/consumer/*/manifest.json`을 읽고, 그래프마다 파일 sha256이 이미 만든 적재본과 같으면 건너뛴다.
다르면 JSONL을 한 줄씩 흘려 읽어 임시 파일 `$KG_DIR/sqlite/<묶음>/<그래프>.sqlite.tmp`에 적재하고, 검사가 모두 맞으면 이름을 바꿔 끼운다(원자적).
검사가 하나라도 어긋나면 임시 파일을 지우고 그 묶음을 쓰지 않는다 — 부분 적재는 일어나지 않는다(`crates/kg`, `rusqlite` bundled).

```sql
meta  (key TEXT PRIMARY KEY, value TEXT)        -- 이름, 해시, 기준일, 계약, 측정 상태, 모양
nodes (id TEXT PRIMARY KEY, kind TEXT, name TEXT, data TEXT)
edges (src TEXT, dst TEXT, type TEXT, data TEXT)               -- INDEX(src,type), INDEX(dst,type)
refs  (article_id TEXT, node_id TEXT)                          -- 조문 역색인
states(node_id TEXT, data TEXT)
nodes_fts USING fts5(name, tokenize='trigram')
```

적재 검사:
1. 첫 줄이 머리이고 형식 이름이 설정값과 같다.
2. 노드·간선·상태 수가 머리의 `counts`와 같다.
3. 파일 sha256이 `manifest.json`의 값과 같다. 서명을 검증한다(검증 공개키는 설정값, 방식은 0단계에서 확인).
4. 모든 간선의 관계가 계약의 허용 관계 안에 있다.
5. 계약이 비순환을 요구하는 관계 층은 층마다 순환 검사를 한다.

읽을 때: `query_only`, `mmap_size` 64MB, 연결은 스레드마다 하나. `rusqlite` bundled에 FTS5가 켜져 있는지는 0단계에서 확인한다.

### 8.3 탐색과 도구

- 원시연산 `expand(graph, node_id, edge_type?, direction, limit)`: 계약 밖 관계는 거부한다.
  `SELECT dst, type, data FROM edges WHERE src=? AND type IN (허용) LIMIT ?`. 다른 탐색은 모두 이 위의 조합이다.
  연결망 모양은 깊이 2까지, 방문한 노드를 표시하며 반복한다(재귀 CTE 하나 또는 깊이마다 한 번).
- 이름 찾기 `find(graph, text, kind?, limit)`: FTS5 trigram. trigram은 세 글자 미만 검색어를 찾지 못하므로 **두 글자 이하는 `LIKE`로** 찾는다.
- 조문으로 찾기: `refs`에서 법령 판본 키로 노드를 찾는다.

| 도구 | 모델에 보이는 인자 | 돌려주는 것 |
|---|---|---|
| `kg_find` | `graph`, `text` 또는 `law`+`unit`, `kind?`, `limit≤20` | 노드마다 짧은 번호(L1, L2…)·이름·종류·한 줄 뜻풀이·상태 |
| `kg_expand` | `graph`, `node`(짧은 번호), `relation?`, `direction`, `depth≤2`, `limit≤20` | 간선(관계·확실성·근거 인용)과 이웃 노드(짧은 번호·이름·내용) |

- 노드 내용 보기 도구는 따로 두지 않는다. `kg_find`·`kg_expand`가 내용을 함께 준다.
- **짧은 번호**: 도구 결과에는 노드 ID 대신 코드가 매긴 짧은 번호(L1, L2…)를 보이고, 모델이 그 번호로 부르면 코드가 원래 ID로 되돌린다.
  번호표는 ①(Rust)이 세션마다 RocksDB `state`에 둔다(`{session}/kg_ids`). Python 쪽은 번호를 그대로 주고받기만 한다. 모델이 긴 ID를 받아 적으면 틀리기 쉽기 때문이다.
- 탐색 규칙:
  1. `kg_expand`는 방향을 반드시 받는다. 깊이 상한은 2다. 양방향 이웃을 섞어 넓게 펼치지 않는다.
  2. 간선에 근거가 없으면 「근거 없음」으로 보인다. 끝점 노드의 근거를 빌려 쓰지 않는다.
  3. 그래프끼리는 공식 식별자(`refs`의 법령 판본 키)로만 잇는다. 법령명과 조문 번호 글자로 잇지 않는다.
  4. 「모름」을 「없음」으로 바꿔 읽지 않는다. 상태 칸과 간선의 확실성 값을 그대로 보인다.
- 조문 본문은 그래프에 없다. 노드의 법령 판본 키로 `read_law`(§7)를 부른다. 이 대응의 적중률(판본 일치율)은 4단계에서 잰다.
- 매번 붙이는 카탈로그(§5.2)는 목록 파일과 각 머리에서 만든다: 그래프마다 이름·모양·노드 수·측정 상태 한 줄.

### 8.4 확장

- 새 그래프: 소비 묶음을 `$KG_DIR/consumer/`에 더하면 서버가 다음 기동 때 읽는다. 코드는 고치지 않는다.
- 새 노드 종류·관계·모양, 또는 형식 판이 오르면: `crates/kg`의 알려진 판 목록과 열거형을 맞춘다. 모르는 판의 머리가 오면 그 묶음을 읽지 않고 기동 로그에 남긴다.
- 이 프로젝트의 요건 트리 4종(§9.3)도 같은 소비 형식(모양 「나무」)으로 만들어 `$KG_DIR/consumer/semantic-rules/`에 두고, 같은 로더로 읽는다.

## 9. 요건 판단 엔진 (Leaf 구조 + Z3)

기준 문서: 「뉴로심볼릭_법리판단_구현_가이드북_확장판」과 그 재구성 CLAUDE.md(`~/Downloads/백업본-뉴로심볼릭-20260913/`).
파이썬 설계를 Rust로 옮긴다.

법리 지식(요건 트리·지식그래프: 여러 개, 모든 세션이 같이 읽음)과 사건 지식(업로드 문서·사용자 진술의 사실: 세션마다 하나)은 나눠 두고,
둘은 **리프 판정 결과**(LeafResult + Anchor)로만 잇는다. 사건의 사실을 요건 트리에 써넣지 않는다.

### 9.1 리프 판정기

- LLM 호출 하나 = 명제 1개 + 사실 묶음 + 근거 묶음 → True / False / Unknown, 그리고 근거 인용문.
  temperature 0, 짧은 max_tokens, 시간 제한, 지수 backoff, strict JSON(실패하면 1회 다시 요청).
- **사실 묶음**: 세션의 업로드 문서(쪽 표시 글자)와 사용자 진술.
  - 문서 전체가 리프 판정 입력 한도(설정 `LEAF_FACT_BUDGET_TOKENS`, Gemma 4 문맥 한도를 잰 뒤 정함) 안이면 전체를 넘긴다.
    리프마다 같은 문서가 앞에 오므로 vLLM의 접두 캐시가 비용을 줄인다(0단계에서 확인).
  - 넘으면 리프 문장과 가까운 문단을 고른다(BGE-M3 cosine, 메모리에서 상위 k — §4 ⑦).
  - 사용자 진술은 `[사용자 진술 #n]` 머리를 붙여 따로 넣는다.
- **근거 묶음**: 법령·판례 검색 결과(§7.2)와, 리프가 지식그래프에 근거를 가지면 그 근거 원문.
- **인용 대조로 Anchor 만들기**: LLM은 판정 근거를 원문 그대로 인용한다(`quote`). 코드가 공백만 정규화해 그 인용문을
  쪽 표시 글자(또는 사용자 진술 원문)에서 찾는다.
  - 찾으면 그 글자 위치로 Block·쪽을 찾아 Anchor를 만든다 → `LeafResult::Judged`.
  - 못 찾으면 `Unknown { NoEvidence("인용문이 원문에 없음") }`. LLM이 지어낸 인용은 판정 근거가 되지 못한다.
  - 사용자 진술을 인용했으면 Anchor 출처는 `UserMessage { message_id }`이고, 판정 문장에 「사용자 진술에 근거함」이 붙는다.
  - 사용자 진술은 ④가 judge를 부를 때 원문 그대로 보낸다. ④는 그 문장이 실제 사용자 메시지에 들어 있는지 먼저 확인하고(글자 일치),
    없으면 넘기지 않는다.
  - 이 대조 검사도 저장 경로에 붙이기 전에 정확도를 잰다: 원문에 있는 인용(공백·줄바꿈만 다름)을 통과시키는지, 한 글자라도 바뀐 인용을 막는지.
- `build_leaf_requests` → semaphore로 제한한 병렬 `judge_leaf` → `LeafResult`.
- 단계 사이에 CoT나 대화 이력을 넘기지 않는다. typed 객체만 넘긴다.
- 모순 검출: 긍정·부정 쌍 리프를 `assert_and_track`으로 넣어 unsat이면 다시 판정, 그래도 충돌이면 둘 다 Unknown.

```rust
enum LeafResult {
    Judged  { value: bool, anchor: Anchor, quote: String }, // 판정 근거 좌표 필수
    Unknown { failure: FailureReason },                     // Unknown의 이유 — 보고서까지 올라간다
}
```

판정된 값과 Unknown을 변형으로 가른 이유: True/False인데 Anchor가 없는 값을 타입상 만들 수 없게 한다.

### 9.2 Z3 사용 규칙

- 필요한 API: `Solver`, `Bool/Int`, `And/Or/Not/Implies`, `assert_and_track` → `get_unsat_core`, `model`.
- 결과는 sat / unsat / **unknown** 삼값을 타입으로 강제한다. unknown = 결론 유보.
- 불성립 이유는 LLM 사후 설명이 아니라 **unsat_core**에서 뽑는다.
- 날짜는 ordinal 정수로만 넣는다. 초일 산입·말일 보정·윤년 등 달력 규칙은 Rust 함수(`checks::periods`)가 맡는다.
- LLM에게 Z3 식을 만들거나 실행하게 하지 않는다. 규칙은 선언 데이터에서 결정론적으로 컴파일한다.
- Anchor 없는 값은 Z3에 들어가지 못한다.
- Z3 Context는 스레드 사이에 공유할 수 없다 → 판정마다 만들고 버린다(ms 단위).

### 9.3 요건 트리 형식 (지식그래프 규칙 그래프)

요건 트리는 지식그래프 `rule` 노드와 element·defense·rebuttal 간선으로 쓴다(§8.1). 원본은 `rules/claim_*.yaml`,
`ruleloader`가 검증해 지식그래프 소비 묶음과 같은 형식(모양 「나무」)으로 낸다(§8.4). 서버는 지식그래프와 같은 로더로 읽는다.
소비 형식에 없는 칸(`domain: administrative`, `ask`, `arithmetic`)은 이 프로젝트의 확장 칸이고, 로더는 `semantic-rules` 묶음에서만 받는다.

```
rule 노드: id, label, domain(administrative), category(claim/element/defense/rebuttal/…), gate(AND/OR/LEAF),
           proposition(리프 판정 문장), burden(§9.5 결정 후), negation_of(긍정·부정 쌍),
           ask(필요한 사실을 묻는 문장 — 리프만, 사람이 씀), arithmetic(산술 리프 — 제소기간 등), evidence[](근거 필수)
간선: element / defense / rebuttal, evidence[] 필수
```

- 트리라 부르지만 DAG다. **공유 리프 허용** — 처분성 리프 묶음은 취소소송·무효확인 트리가 같이 쓴다.
- 적재 가드: 순환 검사(관계 층마다 따로), 청구 유형별 기대 노드·간선·리프 수 고정 검사, LEAF에 proposition·ask, 비-LEAF에 자식.
  하나라도 어긋나면 **부분 적재 금지, 전체 중단**.
- 리프 문장 규칙: 「누가·언제·무엇을」이 들어간 사실 문장. 법적 평가어(「처분성이 있다」, 「재량을 남용했다」)는 결론이므로
  하위 징표로 쪼갤 때까지 내려간다. 금지: 결론을 리프로 / 한 리프에 두 사실 / 항변을 요건의 단순 부정으로 / 위법성·인과관계를 통째로 LLM에게.
- `ask` 문장 규칙: 사용자가 「예/아니오 + 날짜·문서」로 답할 수 있게 쓴다. 예: 「처분이 있음을 안 날은 언제입니까? 그 날짜가 적힌 문서가 있습니까?」
- 청구 유형 하나당 노드 10~30개 수준의 수작업. 리프 문장의 재료는 `~/Downloads/대학 행정법 총정리.pdf`(93쪽).

```
│   └─ S4_협의의 소익
└─ 본안_위법성         OR
    ├─ 절차 하자 (사전통지·이유제시 결여 등)
    ├─ 법률유보 위반
    └─ 재량 하자      OR
        ├─ 재량권의 일탈
        ├─ 재량권의 남용 OR (사실오인 / 비례원칙 위반 / 평등원칙 위반)
        └─ 재량권의 불행사
```

학설 대립이 있는 리프는 판례 입장을 판정 기준 문장으로 적고, 그 판례를 근거 묶음으로 리프에 잇는다.

### 9.5 트리 작성 전 결정 — 입증책임 (결정 1)

가이드북의 burden(PLAINTIFF/DEFENDANT)과 요건·항변·재항변 층은 민사 요건사실론 기준이다. 행정소송은 소송요건이 직권조사사항이고,
본안에서 처분의 적법성 입증책임은 원칙적으로 처분청, 재량 일탈·남용은 원고가 입증한다. 따라서 burden을 행정소송 의미로 다시 정하거나
(직권조사 표시 추가) 입증책임 귀속을 리프별 속성으로 옮기는 결정을 **트리를 그리기 전에** 해야 한다. 이 귀속이 Unknown 리프의 불이익
방향(입증하지 못하면 누구에게 불리한가)을 정하므로 Z3 결론 조립에 직접 영향을 준다.

민사 요건사실론에서 온 다른 규칙(항변 간선을 건널 때마다 입증책임이 바뀐다 등)도 이 결정 뒤에 적용 여부를 정한다.

### 9.6 부분 질문·가정 질문·진입점

- 트리가 노드 단위 DAG라서 **어떤 노드든 루트로 삼아 서브트리만 판정**할 수 있다. 「처분에 해당하나?」 → `S1_처분성` 서브트리만.
  「제소기간 지났나?」 → `S3_제소기간` 산술 리프 하나(LLM은 날짜 추출만).
- 진입점(node_id)은 ④의 모델이 judge 카탈로그를 보고 고른다. 엔진은 그 노드에서 **루트까지의 경로**(노드 ID·설명·게이트)를 응답에 붙인다
  — 이 판정이 전체 청구의 어디에 해당하는지 사용자가 알 수 있게.
- 가정 질문(「처분성은 인정된다 치고 …」)은 Z3 모델 읽기로: 일부 리프 고정 + 나머지 자유변수 → sat 모델 = 성립에 필요한 사실 조합.
  가정으로 채운 값에는 「문서 근거 없음·가정」 표시를 붙인다.
- 부분 판정 결과는 leaf_cache에 쌓여, 이후 전체 질문 때 이미 판정된 리프를 다시 쓴다.
- **판정 범위 명시 필수**: 「처분성 인정 ≠ 취소 인용」. ⑩ 템플릿이 「이 판정은 ○○ 서브트리에 한정, 나머지는 판정하지 않았음」을 자동으로 붙인다.
- **필요한 사실**: Unknown 리프마다 그 리프의 `ask` 문장을 응답의 `needed_facts`에 넣는다. 이 문장은 사람이 쓴 것이고 LLM이 만들지 않는다.

### 9.7 수정판 재검증 (두 속도)

- 결정론 검증(빠른 경로)은 문서 판마다 전체를 다시 돌린다.
- LLM 리프(느린 경로)는 cache_key가 바뀐 것만 다시 판정한다. cache_key = hash(rule_id + 사실 묶음 해시 + 근거 묶음 해시 + 모델 이름·판 + 프롬프트 판).
  사용자 진술이 더해지면 사실 묶음 해시가 바뀌므로, 그 진술이 들어간 리프만 다시 판정된다.

## 10. 세션층 — LangGraph 체크포인트 + RocksDB

코퍼스는 PostgreSQL(법령·판례 DB, 읽기 전용으로 씀), 채팅 세션(대화와 에이전트가 읽은 것)은 ④의 LangGraph 체크포인트
(PostgreSQL, 코퍼스와 다른 데이터베이스), Rust 쪽 업로드 문서 파싱 결과와 리프 판정 캐시는 RocksDB로 나눈다.

### 10.1 채팅 세션 기억 (④, langgraph-checkpoint-postgres)

세션 ID = LangGraph `thread_id`. 에이전트가 한 단계를 끝낼 때마다 체크포인트가 저장된다.

| 상태 키 | 담기는 것 |
|---|---|
| `messages` | 사용자 질문, 에이전트 답변, 도구 호출과 도구 결과(= 에이전트가 읽은 것, judge 판정 문장 포함), 「[업로드]」 한 줄 |
| `uploads` | 업로드 문서 목록(파일명·형식·쪽수·올린 시각·추출 불가·수정판 관계·목차) — 이 프로젝트가 더하는 상태 키 |
| `files` `/uploads/{file_id}.md` | 쪽 표시 글자 원문. 쓰기 금지 |
| `files` `/memory/session.md` | 세션 메모 (§5.6) |
| `files` `/large_tool_results/` | 2만 토큰 넘는 도구 결과의 원문. 메시지에는 앞뒤 일부와 경로만 남는다 |
| `files` `/conversation_history/` | 긴 대화를 요약할 때 모델 입력에서 빠진 앞부분 대화의 원문 |

- 대화가 모델 문맥 한도의 85%(한도를 모르는 모델이면 17만 토큰)를 넘으면 deepagents가 앞부분을 요약해 모델에 보낸다.
  `messages` 원본은 지우지 않는다 — 모델 입력만 바뀐다. 업로드 목록·목차·세션 메모는 매번 붙으므로(§5.2) 요약에 휩쓸리지 않는다.
- `files`는 StateBackend(create_deep_agent 기본값)라 체크포인트와 함께 저장된다. FilesystemBackend로 바꾸면 세션 기억에서 빠진다.
- 하위 에이전트가 읽은 도구 결과는 세션에 남지 않는다. 마지막 답변 하나와 `files`만 돌아온다. 그래서 서브는 출처·원문 인용을 붙인 정해진 형식으로 돌려준다(§5.4).
- 대화 하나가 기억의 단위다(claude.ai처럼 사건 개념이 없다). 사실·가정·판정은 대화를 넘지 않는다. 대화를 넘는 것은 사용자 설정뿐이다(§10.3).
- 확인 상태 (2026-09-29): 위 동작은 deepagents 0.7.19 소스와, 가짜 모델 + in-memory·PostgreSQL 체크포인트 시험으로 확인했다.
  106,890자 도구 결과가 `/large_tool_results/`에 원문 그대로 저장됐고(SHA-256 일치), 프로세스를 다시 띄워도 같은 `thread_id`의
  앞 답변·도구 결과가 모델 입력에 들어갔다. `adelete_thread` 뒤에는 체크포인트 세 테이블의 해당 행이 0이었다.
- 아직 확인하지 않은 것(0단계): 사용자 정의 상태 키 `uploads`를 미들웨어 상태 스키마로 더하는 방법, 파일 권한 규칙의 0.7.19 형태.

### 10.2 RocksDB (①, rust-rocksdb)

| CF | key | value |
|---|---|---|
| `state` | `{session_id}/doc/{file_id}`, `{session_id}/kg_ids` | 문서 모델, 쪽 표시 글자, 글자 위치↔Anchor 대응표, 검증 결과, (한도를 넘는 문서만) 문단 벡터 사본 / 지식그래프 짧은 번호표 |
| `leaf_cache` | cache_key | LeafResult의 serde_json 바이트 (직렬화는 `server/engine_deps.rs` — sessdb는 LeafResult 타입을 모른다) |

- 세션 조회 = prefix iterator, 세션 삭제 = `state`에 `delete_range`(`leaf_cache`는 세션과 무관한 전역 캐시라 지우지 않는다).
- 업로드 한 건의 산출물은 `WriteBatch` 원자 쓰기.

### 10.3 사용자 설정 — LangGraph Store

- 대화를 넘어 유지하는 것은 **사용자 설정(답변 길이·말투·형식)뿐**이다. 사실·가정·판정 결과는 넣지 않는다 —
  다른 대화의 사실이 판정에 섞이면 「사실의 출처는 그 대화의 문서와 진술」(§1.2 원칙 3, §9.1)이 깨진다.
- 저장: langgraph-checkpoint-postgres의 Store(`AsyncPostgresStore`), 체크포인트와 같은 데이터베이스. 이름공간 `("user", 사용자 ID, "prefs")`.
- 에이전트 쪽: deepagents의 경로 연결로 `/prefs/` 아래 파일만 Store에 두고(나머지는 StateBackend), 매번 모델 입력에 붙인다(§5.2).
  이 경로 연결(CompositeBackend·StoreBackend)이 0.7.19에 그대로 있는지는 0단계에서 확인한다.
- 사용자 ID: 로그인한 사용자의 ID(§19). ⓪ 창구가 ④에 머리로 넘기고, ④는 그 값으로만 이름공간을 정한다.
- 지우기: 사용자 설정은 대화를 지워도 남는다. 지우는 길은 ④ `DELETE /prefs`.

## 11. 동시성 설계

기조: **I/O 대기만 비동기(tokio), CPU 핵심 로직은 동기 순수 함수 + `spawn_blocking` 격리.**

| 성격 | 해당 | 처리 |
|---|---|---|
| I/O | LLM·임베딩 API, PostgreSQL, ④의 도구 호출 수신 | tokio + 연결 풀(sqlx, reqwest) |
| CPU | 파싱·표 재구성, Z3, cosine, 결정론 검증, 지식그래프 탐색 | 동기 함수 → `spawn_blocking` |
| 중간 | RocksDB | 블로킹 API지만 µs~ms. 핸들 `Arc` 공유, 긴 iterator만 `spawn_blocking` |

- 엔진·파서를 async로 물들이지 않는다 — 단위 테스트와 정확도 실측이 런타임 없이 가능해야 한다.
- 병렬 발사: 리프 판정 fan-out(`JoinSet` + `Semaphore` 8~16 + 시간 제한 + backoff), 쿼리 재작성 ∥ 임베딩(`tokio::join!`).
- 스레드 안전성 함정 둘: pdfium은 스레드 세이프하지 않음 → 전용 스레드 1개 + 채널. Z3 Context는 공유 불가 → 판정마다 생성·폐기.
- **세션 안은 직렬, 세션 사이는 병렬** — 두 곳에서 지킨다.
  - ④: 세션별 `asyncio.Lock`. 한 `thread_id`에 실행은 하나만. 업로드가 오면 진행 중인 질문을 취소하고 락을 넘겨받는다(수정판 우선).
    취소로 답 없이 남은 도구 호출은 다음 실행 때 PatchToolCallsMiddleware(기본으로 켜짐)가 메운다.
  - ①: 세션당 actor(mpsc + 단일 소비 태스크)가 업로드·판정을 직렬화한다.
- 문서 수정판이 도착하면 진행 중인 리프 판정은 `CancellationToken`으로 취소 → 그 judge는 「판정 불가: 문서 수정판 도착」.
- 캐시 스탬피드 방지: moka `get_with`.
- 오래 걸리는 작업(지식그래프 적재 등)은 시작 전에 코어·메모리·디스크를 확인하고 그 값에 맞춘다.

### 11.1 멀티코어 자원 배분

CPU 코어를 서로 빼앗지 않게 작업 종류마다 자리를 나눈다. 아래 표는 규칙이고, 이 PC(Core Ultra 7 155H, 논리 22, 메모리 15.5GB)에 맞춘 값은 구현지시서 「이 PC 기준 값」에 있다. 값은 설정으로 덮어쓸 수 있다.

| 자리 | 크기 | 들어가는 일 |
|---|---|---|
| tokio 작업 스레드 | 코어 수 | I/O 대기(HTTP·DB·모델 호출). CPU를 오래 쓰는 일을 여기서 돌리지 않는다 |
| tokio 블로킹 풀(`max_blocking_threads`) | 코어 수 × 2, 상한 64 | RocksDB 긴 순회, 짧은 동기 함수 |
| CPU 작업 풀(`rayon`, 하나만) | 코어 수 − 1 | 파싱·표 재구성·결정론 검증·지식그래프 적재·cosine 전수 비교 |
| Z3 | 동시 판정 상한 = 코어 수 / 2 (semaphore) | 판정마다 Context 생성·폐기, 시간 제한(`timeout` 매개변수)과 메모리 상한 |
| pdfium | 전용 스레드 1 | PDF 전부(스레드 세이프하지 않음) |

- CPU 작업은 `rayon`에 맡기고 결과를 `oneshot` 채널로 받는다. tokio 블로킹 풀과 `rayon`을 같은 일에 섞지 않는다(코어 과다 점유).
- 동시 업로드 처리 상한 = 코어 수 / 2. 넘으면 대기열에 넣고, 대기열이 차면 「잠시 뒤 다시 올려 주세요」로 거절한다(메모리 보호).
- PostgreSQL 연결 풀: 법령·판례 DB(읽기 전용)와 앱 DB(체크포인트·Store·`auth`) 따로. 풀 크기는 구현지시서 「이 PC 기준 값」. 지식그래프 SQLite는 `query_only`·스레드마다 연결 하나.
- RocksDB 배경 작업 수 = 코어 수 / 2, 블록 캐시 크기는 메모리의 일정 비율(설정).

### 11.2 역압 (backpressure)과 대기열 상한

- 세션 actor의 채널은 크기를 정한 채널(`mpsc::channel(16)`)이다. 차면 「이 세션은 처리 중입니다」로 바로 돌려준다.
- 리프 판정 fan-out, 쿼리 재작성, 임베딩은 §2.2의 상한 안에서만 보낸다. 모델 서버 대기열이 길면 상한을 낮춘다.
- ④는 uvicorn 작업 프로세스 하나로 띄운다. 세션 락이 프로세스 메모리에 있기 때문이다. 여러 프로세스로 늘리려면 세션 락을 PostgreSQL advisory lock으로 옮겨야 한다(지금은 하지 않음).
- ④의 질문 접수에 세션당 속도 제한(예: 분당 10회)과 전체 동시 실행 상한을 둔다.

## 12. 오류 처리 설계

대원칙(원칙 2): 오류는 Unknown·판정 불가로만 무너진다.

| 층 | 오류 | 처리 |
|---|---|---|
| LLM 리프 | 시간 초과·429·5xx / JSON 파싱 실패 | backoff 재시도(횟수 제한) / 1회 다시 요청 → 최종 실패 = **Unknown + 사유**. 기본값 True/False 채움 금지 |
| LLM 리프 | 인용문이 원문에 없음 | Unknown + NoEvidence |
| LLM 리프 | 긍정·부정 쌍 모순 | 다시 판정 → 그래도 충돌이면 둘 다 Unknown |
| Z3 | unknown 결과 | 결론 유보로 보고(unsat 취급 금지) |
| Z3 | 패닉·자원 초과 | `spawn_blocking` 경계에서 잡음 → 판정 불가 |
| 기능별 빠짐 | 지식그래프 묶음 없음·검사 실패 / 법령·판례 DB 접속 실패 | 그 기능만 끈다(카탈로그에서 빼거나 「검색 실패」). 서버 전체는 멈추지 않는다. 부분 적재는 여전히 금지(그 묶음은 쓰지 않음) |
| 모델 서버(Colab) | 응답 없음 | 검색: 글자 검색만으로 강등(표시) / 쿼리 재작성: 원 질의 / 판정: 「판정 불가: 모델 서버 응답 없음」 |
| 파싱 | 손상·암호화·빈 추출 | 「추출 불가」 명시. 부분 성공이면 성공 범위 명시 |
| 파싱 | 표 재구성 실패 | 평문으로 낮춤 + 산술 검증·Z3 입력에서 제외 |
| 검색 | 재작성 실패 / 임베딩 실패 | 원 질의 / 글자 검색 단독(명시) |
| PG | 일시 오류 / 제약 위반 | 재시도 / 즉시 실패(구분) |
| RocksDB | 쓰기 실패 | 세션에 오류 반환(삼키지 않음) |
| ④ 도구 호출 | ① HTTP 오류·시간 초과 | 예외로 올리지 않고 「검색 실패: 사유」·「판정 불가: 사유」 문자열을 도구 결과로 |
| ④ 체크포인트 | 쓰기 실패 | 그 질문을 Error로 끝냄 — 저장 못 한 답을 기억한 것처럼 두지 않는다 |
| ④ 종료 장치 | 단계·시간 상한 | 「제한에 걸려 중단됨」을 답변에 밝힘 |
| 요건 트리·지식그래프 적재 | 검증 실패 | **부분 적재 금지, 전체 중단** |

**마감의 겹침**: 바깥 마감이 안쪽 마감보다 늘 길다. ④ 질문 하나(300초) > ④→① 도구 호출(judge 180초, 검색 30초) > ①의 리프 판정 하나(60초) > LLM 호출 하나(대기 포함 45초).
안쪽이 먼저 끝나야 바깥이 「판정 불가: 사유」를 받아 밝힐 수 있다. 값은 설정, 위 순서는 기동 때 검사한다(어기면 기동 멈춤).

**밖에 보이는 오류**: 사용자·모델에게 가는 문장에는 사유만 적는다. 내부 경로, SQL, 스택, 접속 정보, 문서 원문 조각은 넣지 않는다. 자세한 내용은 요청 ID와 함께 로그에만.

**요청 ID**: ④가 질문마다 요청 ID를 만들어 ① 호출 머리(`x-request-id`)에 싣고, ①은 tracing span에 단다. 오류 문장에도 요청 ID를 붙인다.

**HTTP 상태**: ①은 입력 오류 400·413(크기)·415(형식), 세션 바쁨 429, 내부 오류 500만 쓴다. 판정·검색 실패는 200 + 본문의 Unknown·강등 표시다(원칙 2).

**종료 절차**: 종료 신호를 받으면 새 요청을 받지 않고 → 진행 중인 판정은 취소해 「판정 불가: 서버 종료」로 응답 → actor 채널을 비우고 → RocksDB를 flush하고 닫는다. ④도 진행 중인 스트림에 Error를 보내고 닫는다. 상한 30초.

- Rust: 층별 `thiserror` enum(`ParseError`/`RetrievalError`/`LeafJudgeError`/`EngineError`/`StorageError`/`KgError`),
  핵심 코드 `unwrap`/`panic` 금지(clippy로 강제), axum 패닉 포획 레이어.
- 멱등성으로 재시도 안전: cache_key, `WriteBatch`.
- 종착점은 로그가 아니라 사용자에게 보이는 문장: 리프 N개 중 M개가 Unknown이면 결론에 목록과 이유를 그대로 내보낸다
  (예: 「R4_고의과실: 업로드 문서에서 근거 조항을 찾지 못함 — 판정 불가」).

## 13. 인터페이스 명세

### 13.1 ⓪ 창구 HTTP API (웹 프론트가 부름)

로그인 경로 말고는 모두 로그인 세션 쿠키와 CSRF 토큰(변경 요청)이 있어야 한다. ④는 아래와 같은 모양의 내부 API를 127.0.0.1에서 제공하고 ⓪만 부른다.


| 메서드·경로 | 요청 | 응답 |
|---|---|---|
| `POST /api/auth/login` | `{login_id, password}` | 쿠키 설정 + `{csrf_token}`. 실패는 사유 없이 「아이디 또는 비밀번호가 맞지 않습니다」 |
| `POST /api/auth/logout` | — | 204. 로그인 세션 삭제 |
| `GET /api/auth/me` | — | `{login_id}` |
| `GET /api/sessions` | — | 내 대화 목록 `[{session_id, title, updated_at}]` |
| `POST /session` | — | `{session_id}` (uuid4 = thread_id, 소유자 = 로그인한 사용자) |
| `POST /session/{id}/upload` | multipart `file` | 업로드 요약 `{file_id, filename, format, pages, outline[], warnings[], findings_count}` |
| `POST /session/{id}/ask` | `{question}` | SSE (§13.4) |
| `GET /session/{id}/history` | — | 화면용 메시지 목록 |
| `DELETE /session/{id}` | — | 204. 체크포인트 삭제 + Rust `DELETE /sessions/{id}` |
| `DELETE /prefs` | — | 204. 내 사용자 설정 삭제 |

대화 경로(`/session/{id}…`)는 ⓪가 소유자를 확인한 뒤에만 ④로 넘긴다. 남의 대화는 「없는 대화」(404)로 답한다.

### 13.3 에이전트 도구의 입력·출력

모든 도구는 문자열을 돌려준다(그 문자열이 「에이전트가 읽은 것」으로 세션에 저장된다). 항목마다 출처를 붙인다.

| 도구 | 모델에 보이는 인자 | 돌려주는 문자열 |
|---|---|---|
| `search_laws` | `query`, `k=8`, `as_of?`, `law_type?` | 첫 줄 강등 표시(있으면), 이어 `[법령명 단위(제목) · 시행일 · 판본]` + 본문 앞 300자 |
| `search_cases` | `query`, `k=8`, `field?`, `court_level?`, `decided_from?`, `decided_to?` | `[법원 사건번호 · 선고일 · 분야 · 절]` + 해당 청크 |
| `read_law` | `law`, `unit`, `as_of?` | 단위 전문 + 판본 정보. 별표가 `link_only`면 「글자 없음 — 파일 링크만 있음」 |
| `read_case` | `decision_id`, `sections?` | 절마다 `## 역할 — 제목` + 본문 |
| `case_citations` | `decision_id` 또는 `law`+`unit` | 인용 목록 |
| `kg_find` / `kg_expand` | §8.3 (짧은 번호) | §8.3 |
| `judge` | `claim_type`, `node_id`, `assumptions`, `user_facts` | 판정 문장 원문 + 필요한 사실 + 경로 |

HTTP 오류·시간 초과는 예외로 올리지 않고 「검색 실패: 사유」·「판정 불가: 사유」 문자열로 돌려준다.
가짜 도구(2단계)는 이 표의 형식 그대로 고정 문자열을 돌려준다 — 에이전트 루프를 DB 없이 먼저 시험하기 위해서다.

### 13.4 SSE 이벤트

아래는 ④가 ⓪에 보내는 내부 이벤트다. 프론트로 나가는 이벤트는 ⓪가 거른 것이다(§20).

`Status`(도구 호출 시작·끝) / `Token`(답변 조각 — 메인 에이전트 것만) / `VerdictReady`(judge의 결과 원문) /

## 14. 데이터 설계

### 14.1 법령·판례 DB 읽기 계약

생산 계층이 만든 DB에서 소비 쪽이 읽는 표와 열이다. DDL과 적재는 생산 계층의 몫이고 이 저장소에는 없다.

| 표 | 소비 쪽이 읽는 열 | 쓰는 곳 |
|---|---|---|
| `law`, `law_version` | 법령ID·이름·종류 / `(kind, lsi_seq)`·시행일·공포일·상태 | `read_law`, 기준일 판본 고르기 |
| `law_unit` | 단위 키·수준·제목·본문·삭제·단위별 시행일·내용 상태·파일 링크·논리 키 | `search_laws`, `read_law` |
| `law_unit_lineage` | 논리 키 | 판례↔조문을 판본과 무관하게 잇기 |
| `law_delegation`, `law_annex_ref` | 위임 조문 쌍, 별표↔조문 쌍 | `read_law`의 「관련」 칸 |
| `court`, `decision`, `decision_number` | 법원·심급 / 사건번호·선고일·분야·묶음 행 표시 | `search_cases`, `read_case`, 필터 |
| `decision_section`, `section_role` | 절 순서·역할·제목·본문 | `read_case`, 검색 결과의 절 표시 |
| `decision_chunk`, `chunk_embedding`, `law_unit_embedding`, `embedding_model` | 청크 위치, BGE-M3 벡터(1024) | 벡터 검색 |
| `decision_citation`, `extract_run` | 인용 위치·논리 키·판본 단위·관계 / 활성 실행 | `case_citations` |
| `decision_overrule` | 판례 변경 쌍 | 검색 결과에 「변경된 판례」 표시 |

- 글자 검색 열·색인의 방식은 0단계에서 정한다(§7.2).
- 소비 쪽은 이 DB에 쓰지 않는다.

### 14.2 지식그래프 소비 묶음

모두 저장소 밖 `$KG_DIR` 아래에 둔다(§2.1).
- `$KG_DIR/consumer/<묶음>/`: 생산 계층이 낸 그대로 — `<그래프>.jsonl`, `manifest.json`, `manifest.json.sig`. 형식은 §8.1.
- `$KG_DIR/consumer/semantic-rules/`: `ruleloader`가 낸 요건 트리 묶음(§9.3), 같은 형식.
- `$KG_DIR/sqlite/<묶음>/<그래프>.sqlite`: 기동 때 만든 적재본(§8.2). 지워도 다음 기동 때 다시 만든다.

## 15. 남은 실측·결정

**실측** (구현계획서 0단계에서 잰다. 무엇을 재서 무엇이 나오면 성공인지는 구현계획서에 있다)

2. 판례 인용 가운데 판본 칸이 비어 있는 비율(창 밖 판본).
3. 글자 검색 방식 비교(PostgreSQL 안의 방식끼리) — 상위 k 적중률과 지연.
4. 좁은 필터 방식 비교(분할 대 부분 HNSW 대 필터 열 복제).
5. Gemma 4: 문맥 한도, vLLM 도구 호출(파서 이름), 이미지 입력, 접두 캐시.
6. BGE-M3: Colab 처리량(배치 크기별), 같은 문장을 두 번 임베딩했을 때 cosine이 1에 가까운지.
7. Colab 터널과 끊김 동작.
8. deepagents 0.7.19: 파일 권한 규칙, `grep` 도구, 사용자 정의 상태 키, StoreBackend 경로 연결, 선언형 하위 에이전트의 미들웨어 전달, general-purpose 하위 에이전트 끄기, `recursion_limit` 기본값.
9. 지식그래프: 소비 묶음 서명 검증 방식, rusqlite FTS5, 노드 법령 판본 키 → `read_law` 적중률.

**결정**

1. burden·직권조사 의미 재정의 (§9.5 — 요건 트리 작성 전 필수).
2. 입력 범위 확정 — 구형 HWP·스캔 PDF 제외 여부와 안내 문구(지금은 제외가 기본값).
3. 체크포인트를 둘 PostgreSQL 데이터베이스 — 법령·판례 DB와 같은 서버의 다른 데이터베이스로 둘지.

(옛 결정 2 「LLM을 외부 API로 쓸지 로컬로 쓸지」는 Gemma 4 + Colab vLLM으로 정해졌다.)

**미논의**

1. 웹 프론트엔드 — React로 정함(9단계). 화면 구성은 그때 정한다.
2. 평가 표본 — 리프 판정기의 오탐·누락 실측 없이는 엔진 결과를 해석할 수 없다. 후보: 실제 판결문의 사실관계를 넣고(결론은 가림)
   트리의 결론이 판결과 같은지 센다. 이 비교 장치 자체의 정확도도 먼저 표본으로 잰다.

| 악성 PDF | pdfium 전용 스레드에서만. 파싱 시간 제한. 더 막아야 하면 별도 프로세스로 떼고 자원 제한(7단계에서 판단) |
| 프롬프트 주입(업로드 문서·법령·판례·그래프 글 안의 지시) | 도구 결과는 자료이고 지시가 아니라는 규칙을 시스템 프롬프트에 둔다. 판정은 엔진이 하고 모델이 바꿀 수 없다(원칙 1). 쓰기 도구는 세션 메모·사용자 설정 두 파일뿐이고, 셸·임의 HTTP 도구는 없다 |
| 사용자 설정에 사실이 섞여 다른 대화로 감 | Store에는 `/prefs/answer_style.md`만. 리프 판정은 Store를 읽지 않는다(§10.3) |
| 비밀값 유출 | 환경변수로만. 로그·오류 문장·도구 결과에 넣지 않는다. 설정 구조체의 Debug 출력에서 비밀 칸을 가린다 |
| 문서 내용 유출 | 업로드 문서는 우리 모델 서버(Colab vLLM)에만 보낸다. 로그에 프롬프트·문서 본문을 남기지 않는다 |
| 모델 서버 가로채기 | 터널은 HTTPS, vLLM `--api-key`. 키는 URL에 넣지 않고 머리로. 키를 바꿀 수 있게 설정으로 |
| DB 권한 | 법령·판례 DB는 읽기 전용 계정. 체크포인트 DB 계정은 그 데이터베이스에만 권한 |
| 저장된 데이터 | `DATA_DIR`(RocksDB)과 `KG_DIR`은 사용자만 읽을 수 있는 권한. PostgreSQL 계정은 데이터베이스·스키마마다 필요한 권한만. 세션 삭제 때 RocksDB의 그 세션 값을 지운다. 오래된 세션(설정, 예: 30일)을 지우는 정리 작업 |
| 의존성 취약점 | `Cargo.lock`·`uv.lock` 고정. `cargo audit`(또는 `cargo deny`)를 단계 끝마다 돌린다 |
| 서비스 거부 | §11.2의 속도 제한·대기열 상한, 업로드 크기 상한, 모델 호출 상한(§2.2) |

## 18. 그 밖의 시스템 문제

- **재현성과 캐시 무효화**: 판정 결과에 모델 이름·판, 프롬프트 판(문장 해시), 요건 트리 묶음 해시, 지식그래프 묶음 해시를 붙인다. 리프 캐시 열쇠에도 모델·프롬프트 판을 넣는다(§9.7) — 넣지 않으면 모델을 바꿔도 옛 판정을 다시 쓴다.
- **값의 판 관리**: RocksDB 값마다 형식 판 번호를 앞에 둔다. 모르는 판이면 읽지 않고 다시 만든다(세션 산출물·캐시라 지워도 된다). ①의 API에는 판 경로(`/v1/…`)를 둔다.
- **시간과 날짜**: 법령 기준일·선고일·「오늘」은 모두 한국 시간(Asia/Seoul) 날짜로 계산한다. 서버 시계가 달라도 같은 답이 나오게 기준일을 요청에 싣는다.
- **글자 정규화**: 인용 대조·파일명·검색어는 NFC로 맞춘 뒤 비교한다(한글 자모 분리 표기 대비). 공백 정규화 규칙은 인용 대조와 같은 함수 하나로.
- **관측**: tracing span(요청 ID·세션 ID·도구 이름), 지표(도구별 지연, 모델 대기열, 캐시 적중률, 판정 불가 사유별 건수), 상태 확인 경로(①·④ 각각 `/health`).
- **자원 증가**: RocksDB 크기 감시와 compaction, 세션 정리 작업(§17), 리프 캐시 상한(크기·기간).
- **빌드 환경**: Windows 개발 PC에는 libclang이 있어야 rocksdb가 빌드된다(`LIBCLANG_PATH`). pdfium 바이너리는 실행 환경마다 따로 둔다. 배포 대상(운영체제)이 정해지면 그 환경에서 빌드를 확인한다.
- **시험**: 단위 시험(순수 함수), 가짜 모델 서버를 둔 통합 시험(§13.3 형식), 판정 장치의 정확도 실측(오탐·누락), 부하 시험(§2.2). 시험 표본은 시험 코드 안에서 만든다(§2.1).
- **개인정보**: 업로드 문서에는 개인정보가 들어 있다. 대화·세션 삭제 경로를 둔다(§13.1). 사용자 설정에는 개인정보를 적지 않는다.

## 19. 사용자 로그인 (세션 방식)

- 맡는 곳: ⓪ 창구(Rust, axum). 사용자와 로그인 세션은 앱 쪽 PostgreSQL의 `auth` 스키마에 둔다.
- 말 구분: 이 절의 「로그인 세션」은 로그인 상태를 뜻하고, 다른 절의 「세션」은 대화(thread)를 뜻한다.

```sql
CREATE SCHEMA IF NOT EXISTS auth;
CREATE TABLE auth.app_user (
  user_id      uuid PRIMARY KEY,
  login_id     text NOT NULL UNIQUE,
  password_hash text NOT NULL,              -- argon2id (PHC 문자열)
  disabled     boolean NOT NULL DEFAULT false,
  failed_count integer NOT NULL DEFAULT 0,
  locked_until timestamptz,
  created_at   timestamptz NOT NULL
);
CREATE TABLE auth.login_session (
  token_hash   char(64) PRIMARY KEY,        -- 쿠키 값의 sha256. 쿠키 값 자체는 저장하지 않는다
  user_id      uuid NOT NULL REFERENCES auth.app_user ON DELETE CASCADE,
  csrf_token_hash char(64) NOT NULL,
  created_at   timestamptz NOT NULL,
  last_seen_at timestamptz NOT NULL,
  expires_at   timestamptz NOT NULL
);
CREATE TABLE auth.thread_owner (             -- 대화(thread)의 주인
  thread_id    uuid PRIMARY KEY,
  user_id      uuid NOT NULL REFERENCES auth.app_user ON DELETE CASCADE,
  title        text,
  created_at   timestamptz NOT NULL,
  updated_at   timestamptz NOT NULL
);
```

| 항목 | 규칙 |
|---|---|
| 가입 | 공개 가입 없음. 관리자 명령(`gateway user add <login_id>`)으로만 만든다(라이선스상 평가자만 쓴다) |
| 비밀번호 | argon2id(메모리 64MiB·반복 3·병렬 1 — 0단계에서 로그인 지연을 재고 정함). 최소 12자 |
| 로그인 세션 토큰 | 32바이트 난수(OS 난수). 쿠키 `__Host-sid`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`. DB에는 sha256만 |
| 만료 | 유휴 30분, 최대 12시간. 요청마다 `last_seen_at` 갱신(1분에 한 번만 씀) |
| 세션 고정 방지 | 로그인할 때마다 새 토큰. 로그아웃·비밀번호 변경 때 그 사용자의 로그인 세션을 지운다 |
| CSRF | 변경 요청(POST·DELETE)은 `x-csrf-token` 머리가 로그인 세션의 CSRF 토큰과 같아야 한다. `SameSite=Strict`와 함께 둔다 |
| 시도 제한 | 아이디마다 연속 실패 5회면 15분 잠금, 주소마다 분당 10회. 실패 문구는 사유를 밝히지 않는다(아이디가 있는지 알려 주지 않음) |
| 대화 소유자 | 대화를 만들 때 `auth.thread_owner`에 적고, 대화 경로마다 확인한다. 남의 대화는 404 |
| ④·①로 넘기는 것 | 내부 키 머리와 사용자 ID 머리(`x-user-id`). ④는 이 머리로만 사용자를 안다(Store 이름공간 §10.3). 내부 키가 없으면 거부 |
| 정리 | 만료된 로그인 세션을 지우는 작업(1시간마다) |
| 기록 | 로그인 성공·실패·잠금을 로그에 남긴다(비밀번호·토큰은 남기지 않음) |

## 20. 프론트에 보이는 정보 줄이기

프론트(브라우저)에는 백엔드가 무엇을 어떻게 하는지 드러내지 않는다. ⓪ 창구가 걸러 보낸다.

| 대상 | 프론트로 보내는 것 | 보내지 않는 것 |
|---|---|---|
| 진행 상태(`Status`) | 짧은 상태 말 몇 가지만: 「문서를 읽는 중」「자료를 찾는 중」「판단하는 중」「답을 쓰는 중」 | 도구 이름, 도구 인자, 검색어, 노드 번호, 단계 수 |
| 답변(`Token`) | 메인 에이전트의 답변 글자 | 하위 에이전트·요약 호출의 글자, 도구 결과 원문 |
| 판정(`VerdictReady`) | 판정 문장 원문(⑩이 만든 것) | Verdict의 내부 칸(노드 ID, unsat_core 원자료, cache_key) |
| 필요한 사실(`NeededFacts`) | 질문 문장 | 노드 ID |
| 경고(`Warning`) | 「일부 자료를 찾지 못했습니다」「이 파일의 일부를 읽지 못했습니다」처럼 사용자에게 필요한 것 | 강등 사유의 내부 설명, 모델 서버 상태 |
| 오류(`Error`) | 일반 문구 + 요청 ID | 예외 이름, 스택, 경로, SQL, 모델·서버 이름 |
| 대화 기록(`history`) | 사용자 질문, 최종 답변, 판정 문장, 업로드 한 줄 | 도구 호출·도구 결과·시스템 프롬프트·세션 메모 원문 |
| 응답 머리 | 필요한 것만 | `server`·`x-powered-by` 같은 서버 정보, 내부 요청 머리 |
| React 운영 빌드 | 압축된 빌드 | 소스맵, `console` 출력, 개발용 메시지 |

- 거르는 규칙은 ⓪에 있다. ④가 새 이벤트를 더해도, ⓪가 아는 이벤트와 칸만 내보낸다(모르는 것은 버림).
- 자세한 내용은 요청 ID로 서버 로그에서 찾는다(§12).
